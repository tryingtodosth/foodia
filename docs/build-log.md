### Session 2 — the two remaining P1 stubs from Section 2/8A: onboarding + Pantry

- **Fixed a pre-existing tooling break before anything else**: `vite.config.ts` imported `sveltekit` from `@sveltejs/vite-plugin-svelte`, which no longer exports it at the installed version (`3.1.2`) — moved to `import { sveltekit } from '@sveltejs/kit/vite'`. `npm run check` now runs clean (0 errors; the 2 remaining warnings are pre-existing a11y notes on `CookingMode.svelte`'s timer `<div>`, untouched this session).
- **`lib/utils/storage.ts`** — SSR-guarded, try/catch-wrapped `localStorage` JSON helpers, the shared primitive both new stores below build on.
- **`lib/state/profile.svelte.ts` / `lib/state/pantry.svelte.ts`** — this app's first two `.svelte.ts` rune stores, same "object of getters + methods wrapping module-level `$state`" idiom `2do` already established for exactly this class of client-only persistence. Both are deliberately **lazy-hydrated** (`hydrate()`, called once from `routes/+layout.svelte`'s own `$effect`) rather than reading `localStorage` at module-load time — reading synchronously at module scope would make the client's very first render disagree with SSR's (always-empty) render the instant a returning visitor already has a saved profile/pantry, a real hydration mismatch. Because `$effect` never runs during SSR, both the server render and the client's pre-hydrate render agree on the empty state — and "no profile yet" IS the correct default anyway (Progressive Profiling, 4.1), not just a workaround.
- **`routes/onboarding/+page.svelte`** — the User Context Engine's onboarding (4.1): a 3-step wizard (diet + allergies → goals → hardware), a "Pomiń na razie" skip link on every step (Progressive Profiling — skipping never blocks the front door), and — a judgment call, see Section 7 item 14 — pre-fills from the existing profile when revisited, doubling as the only "edit profile" surface that exists today.
- **`routes/pantry/+page.svelte`** — the Smart Pantry's P1 slice (4.5/6.1): a local add/remove checklist, explicitly labeled in its own copy as not yet cross-referencing a MealPlan (that's P2 aggregation logic, not built).
- **The hardware hard-filter, wired into the home feed exactly as 4.1 specifies** ("hide a recipe requiring an airfryer if none is declared") — `lib/utils/hardware.ts`'s `ownsRequiredEquipment`, applied as a client-side `$derived` filter in `routes/+page.svelte` (see Section 7 item 12 for why this can't run server-side yet). Also implements the onboarding sketch's own "AHA moment" idea: `equipmentMatchLabel` renders a "✓ Idealne do Twojego Airfryera"-style badge on `RecipeCard` whenever a recipe's required equipment is fully covered by the viewer's declared hardware.
- **A dismissible-by-navigation onboarding nudge on the home feed** ("Nie ustawiłaś jeszcze swojej kuchni…") shown only once hydration confirms no profile exists — never during SSR, avoiding a flash for a visitor who actually does have one.
- Verified end-to-end: `npm run check` clean, `npm run dev` smoke-tested — `/`, `/recipes/r1`, `/recipes/r1/cook`, `/onboarding`, `/pantry` all return 200, and the SSR'd homepage correctly shows zero hardware-match badges (proving the badge is genuinely post-hydration client state, not a lucky SSR coincidence).

### Session 6 — Interface localization + content translation (4.6) + the Capacitor web shell (6.1)

The largest single session so far — three deliverables, built together since the content-translation UI's own "what language is the viewer in" question is answered directly by the interface layer built alongside it.

**Interface i18n (PL/EN):**
- New `lib/i18n/` module: `locales.ts` (`UiLocale`, `DEFAULT_UI_LOCALE`), `messages.ts` (a ~100-key `pl`/`en` dictionary, `en` checked against `pl`'s own keys via `satisfies`), `plural.ts` (real 3-form Polish CLDR pluralization vs. English's 2-form), `t.ts`/`tPlural` (reads `uiLocaleStore` reactively on every call), `localeNames.ts` (a wider curated list for content locales, separate from the interface's own `UiLocale`).

- `lib/state/uiLocale.svelte.ts` — this app's 4th `.svelte.ts` rune store. `routes/+layout.svelte` seeds it from server data in a plain top-level statement (not `$effect`-gated, so SSR and the client's first render agree from paint one), and separately gained a client-only cookie-resync `$effect` (built for the Capacitor build's own benefit, see below, but harmless and genuinely useful on the SSR build too).
- **`LanguageSwitcher.svelte`** (new) mounted in **both** the navbar and a brand-new **`AppFooter.svelte`** (this app had no footer at all before this session) — exactly as asked. Switching is instant (writes the store directly, no reload) and persists via a cookie (new `lib/utils/cookies.ts`) for the next fresh load.
- Every route and shared component migrated: `+layout.svelte`, `/`, `/plan`, `/pantry`, `/onboarding`, `/shopping-list`, `/recipes/[id]`, `/recipes/[id]/cook`, `CookingMode.svelte`, `CommentComposer.svelte`, `RecipeCard.svelte`/`hardware.ts`'s equipment-match badge. Script-level option arrays that carry translated labels (onboarding's diet/goal/hardware lists, `/plan`'s slot labels, `week.ts`'s weekday abbreviations) had to become locale-aware/`$derived` rather than a plain `const`, or they'd have gone stale on a language switch.
- `shoppingExport.ts` refactored to return semantic result codes (`'copied' | 'failed'`, `'stub-copied' | 'stub-failed'`) instead of hardcoded Polish strings — a real correctness fix, not just a translation pass, since business logic shouldn't bake in a display string the interface's own language can change at any moment.
- Verified in both directions, not just spot-checked: curled every route with `Accept-Language: en` and with no header/cookie (default), grepping for the expected string in each language; confirmed `<html lang>` and the footer/navbar switcher both render correctly in each case.

**Community content translation (recipes):**
- `RecipeCard` gained `sourceLocale?`, `RecipeDetail` gained `translations?: Translation[]` (Detail-only — `toCard()` in `mock/index.ts` now also strips `translations`, keeping the real Card/Detail weight split honest); new `Translation`/`TranslatableField` types.
- `lib/utils/translations.ts` — `getRecipeVersions`/`resolveRecipeVersion`. The three asks ("view original" button, submit alternatives to an *existing* translation, propose changes to the *original*) turned out to be one mechanism: a same-locale `Translation` is a revision suggestion, distinguished from a foreign translation only by a computed `isSameLocaleSuggestion` flag — stated explicitly as deliberate reuse in the file's own header comment, not a missing second feature.

Fixed by passing `'original'` straight through so the resolver's explicit-key branch (which always returns the true original) actually runs. Caught by a standalone 5-assertion logic script exercising this exact scenario (plus same-locale-suggestion resolution, cross-recipe hierarchy defaulting, and version-count correctness) against the real fixture data before any browser testing — all 5 passed.
- `SuggestTranslationModal.svelte` — one form for both translating and improving-the-original; pre-fills from the *best already-submitted text* for the chosen locale (so improving an existing translation starts from readable text, not blind source-language text) but diffs the submission against the *raw original* (so a partial edit never silently regresses previously-translated fields the moment it out-votes an older submission). `TranslationBadge.svelte` reuses this app's existing `<details>` dropdown idiom rather than introducing a new popover component.

### Session 9 — Ingredient Alternatives completed (4.2) + Device/Equipment Alternatives built new (4.9)

- **Ingredient Alternatives' write-side finished**: `filterSafeSubstitutions` (a real, tested function since it was first built, but never actually called from any page) is now wired into the one place every visible substitution list, vote button, and `recomputeMacros` call reads through (`substitutionsFor`, `routes/recipes/[id]/+page.svelte`) — a filtered-out substitution genuinely cannot be chosen, voted, or silently affect macros. `SubstitutionComposer.svelte` is the missing propose-a-substitution form (name + ratio, deliberately no `deltaMacros` — a lay proposer can't know the precise macro impact, and `applySubstitution` already treats an absent delta as zero). `recomputeMacros` gained an `extraSubstitutions` parameter so a freshly-proposed-and-immediately-chosen substitution actually affects the displayed macros instead of being silently unfindable. ### Session 25 — real unit conversion: the ask-once density prompt (Section 7 item 3, open since the first pass of this document)

The direct follow-through on Session 24's fifth follow-up, which flagged cross-system unit handling as "a real, separately-scoped feature to pick up only if asked" — asked. The framing that shipped is the one that unblocked it: *if there's genuine doubt about a conversion, ask the cook which density their ingredient is closest to, once, and remember the answer.* See 4.10 for the full design; what's worth recording here is what the work actually turned up.

- **The 24-session-old blocker was a false binary, not a missing dependency.** Section 7 item 3 asserted this "needs a real per-ingredient density table," and every feature that hit the wall since (Session 5's `crossReferencePantry`, Session 12's `pantryStore.add()`, `FUTURES.md`'s SKU-mapping, 6.5's proposal to solve it with an LLM) accepted that premise unexamined. Two things were wrong with it: **same-family conversion needs no density at all** (g↔oz, cup↔tbsp is fixed arithmetic — that alone covers most real mismatches this app sees), and cross-family conversion doesn't need per-*ingredient* precision, only which of five broad classes an ingredient sits in — a question the cook can answer instantly and only has to answer once per ingredient, ever. The item's own stated *premise* held up exactly (a cup of flour and a cup of honey really do convert differently — `verify-units.ts` asserts that difference directly rather than restating it); only its stated prerequisite was wrong.
- **`partiallyCoveredDifferentUnit` (a boolean) became `unitStatus` (four real values)** — the old flag conflated an *answerable* question ("cups vs. grams — which density?") with a genuine dead end ("ząbki vs. grams — no density bridges these, ever"). Distinguishing them is the whole feature: one gets a prompt, the other keeps the honest "check manually" badge it always had.
- **Two real bugs found and fixed while finishing, both from the same root — conversion math is the first thing in this app that produces non-round numbers.** (1) `formatShoppingListText` still printed raw quantities, so a converted value would have landed on a shopper's clipboard as `263.41176470588235 g`; it now uses `formatQuantity`, same as every on-screen figure. (2) `needsDensity` originally lost to a successful conversion in the status precedence, so a pantry holding *both* "500 g flour" and "2 cup flour" reported `converted`, silently dropped the cup row from the subtraction, and never asked the one question that would have recovered it — precisely the dead end this feature exists to remove. Fixed so `needsDensity` outranks `converted`, with `pantryQuantity` still carrying whatever genuinely did convert, so answering the prompt only ever *adds* coverage. Both are covered by assertions now, in both directions.
- **A deliberate placement call, stated so it doesn't read as an omission**: the density prompt appears on `/shopping-list` only, never in `pantryStore.add()`. An unresolved mismatch actually blocks a decision on the shopping list ("do I need to buy flour or not?"); it doesn't while logging groceries. So `add()` merges wherever real math already allows — including same-family and spelling variants, neither of which it could before — and otherwise keeps a separate row exactly as it always did. Nothing ever interrupts adding to the pantry with a modal.
- **`scripts/verify-units.ts` (new) — 48 assertions, all passing, and it imports the real modules rather than mirroring them**, a first for this project's verification scripts: `units.ts`'s only non-relative import is `import type` (erased by esbuild), and `shoppingList.ts`'s `$lib` value imports resolve through `.svelte-kit/tsconfig.json`'s own `paths`, which tsx reads. So the assertions run against exactly the code the app ships, with no mirrored copy that can drift out of sync. Only `pantryStore.add()` is mirrored — a rune store can't be evaluated under plain tsx — and it's labeled as a mirror at the call site rather than left to look like the real thing.
- **Verified live in a real browser as well**, on one deliberately-constructed shopping list exercising all four statuses simultaneously: `match` (Passata, fully covered), `converted` (0.2 kg against a 400 g need → exactly 200 g still missing), `incompatible` (g against a "ząbki" need → honest badge, no prompt), and `needsDensity` (cups against a g need → the prompt, on that item only). Answering it moved Spaghetti to fully-covered at 402.2 g in the same tick, the class persisted to `localStorage`, and a full reload did **not** re-ask. Zero page errors; the export text carried clean quantities.
- `npm run check`: 0 errors, same 6 pre-existing `CookingMode.svelte` warnings, no new ones. Both build targets rebuilt clean — **the default build was OOM-killed on the first attempt** by unrelated host processes (two other projects' dev servers plus Firefox, ~1 GB free of 7 GB), the same shared-machine contention Session 19 already documented; it succeeded on a retry with nothing changed, so it's worth recognizing that failure mode as environmental rather than chasing it as a build bug.
- Section 7 item 3 marked resolved (struck through, not deleted, same convention every prior resolved item uses), with a note on *why* it stayed open so long, since the reason was a reasoning error rather than a missing prerequisite. 4.5's own prose updated; 6.5's "AI-driven unit conversion" bullet is now genuinely narrower than it was — the non-AI mechanism it proposed working around exists.

### Session 26 — the Admin Dashboard, a real server-side gate, R2 uploads, and the moderation queue finally reaching D1

Asked for one thing — "create admin dashboard accessible only for me" — which turned out to need three things this app had never had: a way to know who's asking *on the server*, a place to grant permissions, and something worth granting. The upload permission was added mid-session at the founder's own direction ("permission to upload to a user role by default off — I will turn it on only for tester!"), which pulled the long-deferred R2 work (`FUTURES.md` 9.5, Phase 2 since Session 16) forward with it: a permission that gates nothing is not a permission.

- **The gate is an environment allowlist, not a database column** (`lib/server/auth/admin.ts`, `ADMIN_EMAILS`). This is the one decision the whole session rests on. `users.is_moderator` and the new `users.can_upload` are rows *this app's own code writes*, so any bug in an admin endpoint is in principle a path to becoming one; `ADMIN_EMAILS` lives in the Worker's environment (a Cloudflare secret in production, gitignored `.dev.vars` locally) and **no code path in this repo writes it**. Becoming an admin requires access to the Cloudflare account, not to the app. Being on the list still isn't authentication either — you also have to log in as that account, real session, real PBKDF2 check.
- **`hooks.server.ts` now resolves the viewer per request** (`locals.user`, `locals.isAdmin`), which this app deliberately never did before: every auth-shaped check until now was client-side (`auth.svelte.ts` calling `/api/auth/me` after mount). That's fine for chrome like "show the Moderacja link" and *not* a gate — a client can simply not run the check. Guarded for the Capacitor prerender, which has no D1 binding by definition and correctly resolves anonymous.
- **`/admin` 404s rather than 403s** for anyone not on the list. A 403 confirms the route exists and that the visitor merely isn't allowed; a 404 says what every other nonexistent URL says. The admin never sees it, so nothing is lost by being uninformative. The check runs in `+layout.server.ts` **before any child load**, so no admin data is ever fetched, let alone serialized, for a request that isn't allowed to see it. Every `/api/admin/*` route re-checks `locals.isAdmin` independently — a fetch to those URLs never passes through the page layout, so inheriting its gate would have left them open.
- **Four tabs, all reading real D1**: Overview (13 live `count(*)` figures — accounts, recipes, ingredients, steps, public/private/removed comments, substitutions, step alternatives, translations, live sessions, pending reports, upload-permitted accounts — plus newest accounts/recipes), Users (every account with real recipe/comment counts, the two permission toggles, delete), Content (recipes and the newest 200 comments, with delete), Moderation (the two queues, plus a resolved-report audit list `/moderation` never had). Mutations re-run the server load via `invalidateAll()` rather than patching a row in place, so what's on screen comes from the database that was just written to.
- **The moderation queue is real now.** `comment_reports` and `recognized_substitutions` have existed in the schema since Session 17 with **nothing reading or writing them** — `/moderation`'s queues ran entirely off session-only client stores, so a report filed on Monday was gone by Tuesday and no moderator on another device ever saw it. Five new routes close that (`POST`/`GET /api/comment-reports`, `PATCH /api/comment-reports/[id]`, `GET`/`POST /api/recognized-substitutions`, `DELETE /api/recognized-substitutions/[id]`), and both rune stores became client-side **caches of server truth** rather than the truth itself — every mutation awaits the server and adopts the row the server actually wrote. Read scope is enforced in the route: a moderator/admin gets the whole queue, a signed-in visitor gets only reports they filed plus reports against their own comments (exactly what `/activity` renders), an anonymous visitor gets an empty list.
- **Every denormalized field on a report is derived server-side from D1, never accepted from the request body** — the client has that context on screen, which is precisely why trusting it would be wrong: a report is evidence, and evidence the reporter can rewrite is not evidence. One real consequence caught while writing it: the derived labels had to be language-**neutral** (a bare ingredient name, `#3` for a step) rather than the client's old `"Składnik: Mąka"` phrasing, because the row is written once and read later by whoever opens the queue, possibly in the other interface language.
- **A moderator removal is a soft delete now** (`comments.removed_at`/`removed_by_id`, migration `0002`): the row stays so an admin can review or undo it, and `dbApiClient`'s new shared `toNodeComment` blanks the text *at the server boundary* before it can reach a viewer, handing back only a `removed: true` flag for the tombstone. One helper for both assembly paths on purpose — a rule like "removed text never leaves the server" holding in one path and being forgotten in the other is exactly how the Session 20 private-comment leak happened.
- **R2, real and gated** (`POST /api/uploads`, `GET /api/media/[...key]`, `ImageUploadField.svelte` wired into the Composer). Three gates in order: a valid session, that account's own `can_upload` (default-off for **every** account ever created, including the admin's — the only way to turn it on is this dashboard), and real content validation: allowlisted MIME type, 5 MB cap, and a **magic-number sniff of the actual bytes**, because a `Content-Type` header is a claim by the uploader, not a fact about the file. Deliberately not a presigned-URL/direct-to-R2 upload despite `FUTURES.md` 9.5's own eventual design: a presigned URL hands the client a credential that bypasses gates 2 and 3 for its lifetime, which is the wrong trade when the permission *is* the feature. The bucket stays private; bytes only come back out through this app's own route.
- **Two real bugs found by actually fetching an uploaded image locally, not by reading type signatures.** (1) `object.writeHttpMetadata(headers)` and `get(key, { onlyIf: request.headers })` both 500 under `vite dev`: wrangler's miniflare proxy serializes every argument and a `Headers` instance isn't serializable ("Cannot stringify arbitrary non-POJOs"). (2) R2's own `etagDoesNotMatch` **rejects a quoted ETag** — which is exactly the form browsers send, per the HTTP spec — and takes only a single string where `If-None-Match` may legitimately list several. Conditional GET is therefore handled in this route rather than by R2's built-in path, verified against quoted, weak (`W/`), stale and wildcard ETags.
- **Verified end-to-end, both by API and in a real browser** (headless Chromium, 15/15 assertions, zero page errors): anonymous `/admin` 404s; a *logged-in real moderator* 404s on both the page and every `/api/admin/*` endpoint; the admin gets in, sees 13 tiles with real numbers, 29 accounts, 77 recipes, 175 comments with private ones labelled, and a resolved report in the audit list; flipping the upload toggle persists through a reload. Separately, by API: upload 401s anonymously, 403s for a signed-in account without the flag, 201s once granted, and 415s on a file whose bytes don't match its declared type; a report round-trips 401 (anonymous) → 201 → 409 (duplicate) → resolved → tombstone with blanked content in `GET /api/recipes/r1` → restored; recognizing a `system`-sourced substitution is refused (400) since "recognized" is specifically the community-earned label. The permission granted to a test account during the run was reverted afterwards — `can_upload = 1` is true for exactly one row.
- **One UX correctness fix that fell out of the change**: the 🚩 report control is no longer offered to anonymous visitors on the web build, since filing now genuinely requires an account (`/api/comment-reports`' own 401). Offering a button that always fails is worse than not offering it.
- `npm run check`: 0 errors, same 6 pre-existing `CookingMode.svelte` warnings, no new ones. Both build targets rebuilt clean from a cleared cache (the Session 24 lesson about stale artifacts before a deploy), with `/admin` correctly **absent** from the Capacitor static output — it opts out of the root layout's prerender cascade explicitly, since prerendering means running that gate at build time with no request, no cookie and no session, which would resolve to "not an admin" and fail the build.
- **Left open, stated plainly**: the production side is not done and cannot be from this environment — no Cloudflare credentials are present (`wrangler whoami`: not authenticated). Remote D1 still needs migration `0002` applied, the `foodia-media` R2 bucket still needs creating, the `ADMIN_EMAILS` secret still needs setting on the Pages project, and the admin account itself exists only in local D1 so far. There is no per-user upload quota and no cleanup of orphaned R2 objects when a recipe is deleted (the hero image outlives its recipe) — both real, both smaller than the gap they sit next to, neither pretended away. `/moderation` remains the moderator-facing page and still gates client-side by design; `/admin`'s own moderation tab is the server-gated one.

### Session 28 — cooking becomes a real session, and the plan → shopping-list → pantry loop finally closes

The brief was "the food management is lacking multistep behaviour," with three candidate flows to check first rather than assume. **All three were investigated against the code before anything was built**; two turned out to be one problem, and the third turned out to be a documented decision that would have been wrong to undo.

**What the investigation actually found:**

1. **Cooking Mode was multi-step in appearance and one-shot in fact.** `currentIndex` was plain component `$state` — a reload, a phone call or a back-tap put the cook back on step 1 with no record that four steps had happened. The last step was a literal dead end (`advance()` clamped and did nothing), so **a finished recipe and an abandoned one were indistinguishable to the rest of the app**. There was no exit affordance at all (the overlay is `position: fixed; inset: 0` over the navbar, so the browser's back button was the only way out), no way to record "I substituted X" — Cooking Mode never rendered ingredients — and the timer both died on unmount and drifted under tab throttling.
2. **The pipeline was two-thirds joined, and the missing third was the one that mattered.** plan → shopping list is real (`?week=`/`?plan=`, `aggregateIngredients`, `crossReferencePantry`); shopping list → pantry is real (per-item "Kupione → dodaj do spiżarni"). **cook → pantry did not exist in any form**: `MealSlot` had no cooked state, `/plan` linked meals to `/recipes/[id]` and never to cooking, and the only thing that ever removed pantry stock was a manual whole-row delete. So the pantry drifted stale from first real use, and every shopping list computed from it drifted with it. "Adjacent, not joined" was the right diagnosis for exactly one of the three legs.
3. **Recipe authoring is deliberately not a staged wizard, and that was not a gap to fix.** `/recipes/new` being a single-page editor is an explicit, reasoned decision (4.2, Session 18: seeing ingredients and steps together matters when a step names an ingredient — `FUTURES.md` 9.4's original pick *was* a staged wizard and Session 18 knowingly went past it). Rebuilding it as a wizard would have undone a documented call to satisfy the shape of the brief. **The real gap in that area is a different one and is much larger**: there is no recipe *editing* at all (no `PUT`/`PATCH` route; `recipe_versions` is read but never written, so "versions" is a read-only concept), and no review step between publish and appearing live — both already recorded in Session 18's own "left open". Deliberately not started here; it is its own session, and doing it badly alongside two other flows would have been worse than not doing it.

So: one coherent piece of work spanning findings 1 and 2, because the end of a cooking session **is** the event the pantry leg was missing. Full designs in 4.3's own new subsection and 4.5's; what's worth recording here is what the work turned up.

- **New: `lib/types/cooking.ts`, `lib/utils/cookingDeduction.ts`, `lib/state/cookingSession.svelte.ts`** (10th rune store), plus real changes to `CookingMode.svelte`, `pantry.svelte.ts` (`consume`/`restoreConsumed`), `mealPlan.svelte.ts` (`markCooked`), `MealSlot.cookedAt`, `/plan`, `/recipes/[id]`, `+layout.svelte`, and 40 new dictionary keys in both `pl`/`en` from the start (this app's standing "new UI ships translated" discipline).
- **A real bug of my own, caught by the browser pass and not by the type checker.** The first full run failed at exactly one assertion — "a reload resumes at step 3" — because the new store was never added to the root layout's hydration `$effect`. Everything worked perfectly *within* one page's lifetime (the store was written in memory by the recipe page's own CTA), which is precisely the class of bug that looks fine in every test that doesn't actually reload. `npm run check` was clean before and after; only reloading the page found it. Worth recording as the second time in this project a hydration-ordering mistake got through everything except a real browser (`QA.md` Issue #1 was the first).
- **The pantry deduction is a preview the cook confirms, not the background write the spec asked for.** `FUTURES.md` Section 1 says it should happen "immediately, in the background"; this app's own rule says never silently rewrite what a cook is looking at. Returning a *plan* rather than performing one satisfies both, and it made the undo trivial to build honestly on top.
- **Plan context travels in the session store, not the URL.** `/recipes/[id]/cook` has an `entries` generator and is genuinely prerendered in the Capacitor build, and a prerendered page cannot read `page.url.searchParams` — the exact restriction `/plan`, `/shopping-list` and `/login` each opted out of prerendering for (Sessions 6/8). Opting this route out too would have been strictly worse: it has a `+page.server.ts`, so the static build would have had no way to load the recipe at all. Recognised from that precedent up front rather than discovered by a failed build.
