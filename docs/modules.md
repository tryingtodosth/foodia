## 4. Module specs

### 4.1 User Context Engine 🎯 P1 (core) / 🧩 P2 (sub-profiles)

Onboarding collects `DietProfile` + `HardwareProfile` before the first real recommendation. Two improvements over the original brain-dump, worth calling out:

- **Progressive profiling, not a hard gate.** If onboarding is skipped, the app runs a "Neutral" profile (balanced, popular recipes) and infers preferences from repeated rejections rather than blocking the front door on a form — this was already in the founder's own failure-mode pass, kept here as a P1 requirement, not deferred, since a real quiz with zero fallback is a real drop-off risk.
- **Allergy guardrails are a hard constraint, enforced in code, never an AI suggestion.** ✅ **Built (Session 9)** — see 4.2's own "Ingredient Alternatives" subsection for `filterSafeSubstitutions`, the function that's actually structurally incapable of letting an unsafe swap reach the UI.
- ✅ **Built (Session 9) — the "temporarily disable broken equipment" override from the failure-mode brain-dump.** What used to be flagged here as needing "a real per-recipe re-derivation of alternate cooking methods" is now the Device/Equipment Alternatives module — see the new 4.9.

### 4.2 Graph Recipe Engine 🎯 P1

The centerpiece. Built this session as static-graph browsing (Section 3's types + mock fixtures); substitution math (recompute `MacroSummary`/`timeMinutes` when a swap is chosen) is real client-side logic, not mocked. **Versioning** (`RecipeVersion`) ships as a simple parent/variant list in P1 — the founder's "evolution tree" (a Decision A → B → C ancestry, rendered as a graph) is 🔮 P3 (6.3), since it needs real relationship data, not just a flat variants array.

~~⚠️ A foundational gap... there is currently no way for a user to create or import a recipe at all~~ ✅ **Built, Session 18 — the Recipe-First Composer** (`FUTURES.md` 9.4's own picked-first option, and the single largest item left on the whole backlog). `/recipes/new` — a single-page editor, deliberately not a step-gated wizard like `/onboarding` (recipe authoring benefits from seeing ingredients and steps together, a real UX call, not an inconsistency): Basics, an Ingredients list, a Steps list, Publish. Both lists support real drag-and-drop reordering (native HTML5 DnD, no new dependency) — ingredients are tracked by a stable client-only id rather than array position specifically so reordering them can never silently corrupt which ingredient a step refers to; that resolution only happens once, at submit time. Backed by a real write path: `POST /api/recipes` (`lib/server/api/createRecipe.ts`), requiring a real logged-in author (session-cookie-validated) and real validation (name/summary/description required, ≥1 ingredient, ≥1 step, no step referencing an out-of-range ingredient). An anonymous visit shows a login gate with a working `?redirectTo=` back to the composer, not a raw 401. Linked from the main navbar ("+ Dodaj przepis"), not tucked into a menu — this was `STORIES.md` S19's own long-documented "no entry point exists anywhere" finding, now the opposite: S19 was rewritten to test the real flow instead of the gap. See Session 18's own build-log entry for the full write-up and the real recipes imported through it.

#### Ingredient Alternatives — the write-side, completed 🎯 built (Session 9)

Substitution *browsing* (4.4/Session 3) always worked; two real gaps existed underneath it, both closed this session:

- **The allergy guardrail (4.1) existed as a real, tested function — `filterSafeSubstitutions` — but was never actually called from any page.** A user could declare a peanut allergy during onboarding and still see, vote on, and choose a peanut-based substitution on `/recipes/[id]`, because nothing in the UI ever ran the loaded substitution list through the filter. Now wired in: `substitutionsFor(ingredientId)` (the recipe detail page's own helper) is the **one** place every visible substitution list passes through `filterSafeSubstitutions(subs, allergies)` before it reaches the swap picker, the vote buttons, *or* `recomputeMacros` — a filtered-out substitution can't be chosen, voted on, or silently affect the displayed macros either, since all three read through the same filtered list rather than three independent checks that could drift out of sync.
- **A real, found-and-fixed bug in the guardrail's own default matcher, not shipped broken.** `filterSafeSubstitutions`'s original default `allergenNameMatch` was a whole-string substring check (`name.includes(allergy)`). This looks reasonable in English but is a real safety gap in Polish: a user types "orzechy" (the natural plural a Polish speaker would enter), and it simply never appears as a substring inside "Mleko orzechowe" or "orzech laskowy" — different grammatical forms of the same word, so the naive check silently let the unsafe substitution through. Caught by this module's own standalone verification script (not discovered later, or by luck): `defaultAllergenNameMatch` (`lib/utils/substitution.ts`) now compares **word stems** (the first ~5 letters of the allergy word against the start of each word in the substitution name) instead of whole-string substrings — "orzechy"/"orzechowe"/"orzech" all share the stem "orzec" and correctly match, while a short, unrelated word ("soczewica" vs. "sojowe") doesn't false-positive. Still an honest heuristic, not real allergen tagging (see this function's own header comment) — deliberately erring toward over-filtering (hiding a possibly-safe swap) rather than under-filtering (showing a genuinely unsafe one), the correct direction to err in for a safety guardrail specifically.
- **`SubstitutionComposer.svelte`** — the missing write-side. Same collapsed-toggle-reveals-a-form shape as `CommentComposer`: a name field and a quantity-multiplier (`ratio`) field, nothing else. Deliberately **never asks for `deltaMacros`** — a community member proposing "use 4 cloves instead of 2" has no reliable way to know the precise macro impact, and `applySubstitution` already treats an absent `deltaMacros` as a zero delta, so a community submission simply doesn't claim a macro change; only curated `source: 'system'` substitutions bother calculating one. Session-only, same `sessionSubstitutions` pattern every other write-side feature in this app uses — merged with the fixture-loaded list at render time via `substitutionsFor`, never mutating the loaded recipe.
- **`recomputeMacros` gained an `extraSubstitutions` parameter.** Without it, a substitution proposed and immediately chosen in the same session would be un-findable by the macro recompute (which only ever searched `ingredient.substitutions`) — the ingredient list would visibly show the swap as chosen, but the macro totals at the top of the page would silently ignore it. Now `recomputeMacros(recipe, chosenSubstitutions, extraSubstitutions)` searches both lists.
- **A real UI gap fixed along the way**: the swap `<details>` disclosure and the propose-a-substitution composer used to only render when `ingredient.substitutable && ingredient.substitutions?.length` — meaning an ingredient marked substitutable but starting with *zero* substitutions (a totally reasonable state for a brand-new ingredient) had no way to ever get its first community substitution proposed. Fixed to gate on `ingredient.substitutable` alone.
- **Fixture demo**: `overnightOats`'s "Mleko" ingredient (`i7`) gained a real, well-reacted community substitution, "Mleko orzechowe (orzech laskowy)" — the exact case the stem-matching fix above exists to catch. Visible with no allergy declared; correctly disappears from the swap list, the vote buttons, and the macro recompute the moment a profile declares an "orzechy" allergy during onboarding.

### 4.3 Cooking Mode 🎯 P1 (core) / 🧩 P2 (voice, ingredient sub-grouping, hybrid inline instructions, robust background timers)

Fullscreen, one-step-at-a-time, huge font, tap-anywhere-to-advance, Wake Lock on mount. Built this session as a real component using the browser's native `WakeLock` API (with a documented Capacitor-plugin fallback path for P2, since Wake Lock browser support is inconsistent across WebViews — see 7). A `Step.durationMinutes` renders as a tappable chip that starts an in-page timer with an audio alert; **push notifications for a backgrounded timer are 🧩 P2** (needs Capacitor Local Notifications — a web `setTimeout` timer dies the moment the OS suspends a backgrounded tab/WebView, so P1's timer is honestly only reliable while the screen stays on, which Wake Lock happens to guarantee).

**Session 9 — equipment-aware, not just duration-aware.** `CookingMode.svelte` now reads `profileStore.profile?.hardware` and, for whichever step is currently on screen, auto-substitutes the single best-fitting `StepAlternative` (via `pickUsableAlternative`, 4.9) in place of the base technique the moment `stepNeedsAlternative` is true — no browsing, no picking, since mid-cook is not the moment to compare options the way the recipe detail page's own browse list is for. An explicit "Show original step" escape hatch (`showOriginalInstead`, reset every time the step changes so a choice never silently carries into the next step) lets the cook override the auto-pick. If equipment is missing and *no* usable alternative exists at all, a warning badge names exactly what's missing (`missingEquipmentLabel`) rather than silently showing a step the cook can't actually follow.

#### Cooking as a resumable SESSION, not a screen 🎯 built (Session 28)

Everything above described a *view*. Until this session that's literally all it was: `CookingMode.svelte` held `currentIndex` in plain component `$state`, so "where am I in this recipe" existed for exactly as long as that component stayed mounted. A reload, a phone call, a stray back-tap — step 1 of N again, with nothing recording that the first four steps had already happened. And the last step was a dead end: `advance()` clamped at `steps.length - 1` and did nothing, so **a finished recipe and an abandoned one were indistinguishable to the rest of the app**, which is why nothing downstream (the plan, the pantry) could ever learn that cooking had occurred. Multi-step in appearance, one-shot in fact.

- **`lib/types/cooking.ts` / `lib/state/cookingSession.svelte.ts`** (this app's 10th `.svelte.ts` rune store) — step position, finished step ids, mid-recipe swaps, a running timer and an optional plan context, keyed by recipe id, persisted to `localStorage`. **Persisted, unlike `stepAlternatives.svelte.ts`'s deliberately tab-lifetime-only store** — a real difference in kind, not an inconsistency: a session-proposed alternative is a draft a reload may legitimately discard, whereas "I am four steps into cooking dinner" is a fact about the physical world that a reload has no business forgetting. Keyed by recipe rather than a single "active session" singleton because a cook genuinely can have two things going at once. **Resuming is the default and clobbering has to be asked for** (`start({ restart: true })`) — re-entering from a link, a reload, or the plan must never silently throw away where the cook actually was.
- **Resume is surfaced where it's needed, not just honoured internally**: `/recipes/[id]`'s cook CTA turns into "⏸ Wróć do gotowania — krok 3/6", and `/plan`'s meal chips show "⏸ krok 3/6" on a half-cooked meal. Both read `stepIndex`/`stepCount` straight off the session, which is exactly why those two fields are denormalized onto it — a resume banner must not need a recipe fetch to render.
- **The last step now ends the session properly**, through a real review → confirm → outcome sequence rather than a single terminal tap. See 4.5's own entry for the pantry deduction that hangs off it and why it's a preview the cook confirms rather than the silent background write `FUTURES.md` specced.
- **The timer became an absolute end time** (`CookingTimer.endsAt`) instead of a ticking `timerSecondsLeft -= 1`. Two independent reasons, only one of which is about resumability: a countdown integer cannot survive a reload at all, which made "leave and come back" a lie for exactly the steps where it matters most (a 25-minute simmer); and a per-second decrement **under-counts** whenever a mobile browser throttles a backgrounded tab, so the old timer silently finished late by however long the tab was suspended. An absolute end time is correct on return regardless of what the OS did in between. It still doesn't *ring* in the background — that needs Capacitor Local Notifications, unchanged (Section 7 item 11). A timer started on step 3 now also stays visible on step 4, labelled as coming from an earlier step: the pot is still on the hob regardless of what the cook is reading.
- **A real warning-count improvement, not a wash**: the 6 long-standing `a11y_no_noninteractive_element_interactions` warnings this file carried (the equipment badges and the timer `<div>`, each needing an `onclick` purely to stop the tap-to-advance firing behind it) are **gone** — every interactive control in the rewritten component is a real `<button>` that stops propagation itself, and the swap picker suspends tap-to-advance outright while open. `npm run check` reports 0 errors and 0 warnings for the first time in this project's history.

**New candidates from the Session 7 research pass (`FUTURES.md` Section 3):**
- **Hybrid inline instructions** — the single most-requested in-cooking UX fix in the source research (scrolling between a separate "Ingredients" list and "Instructions" text while hands are covered in flour is the #1 named complaint). **Half-built, Session 28, and the half that shipped is the half that mattered**: each step now renders its own ingredients (from `Step.ingredientIds`, in the type since Section 3 and read by nothing but Cooking Mode's highlight until now) at their real, swap-adjusted quantities, directly under the step text — so the amounts a cook reads mid-step are consistent with the ingredient list by construction. **The currently-live inconsistency this section flagged is therefore resolved**: a cook who swapped in lentils no longer reads "dodaj mięso mielone" with the old amount — the chip says "240 g Soczewica czerwona · zamiast: Mięso mielone". Still **not** built: interpolating those amounts *into the prose of `Step.text` itself*, which is what the original idea described and which needs either authored placeholders or text parsing this app has deliberately avoided.
- **Ingredient sub-grouping** (`Ingredient.group?: string`, e.g. "for the sauce" vs. "for the marinade") — a trivial addition, rendered as sub-headings during mise en place. Still unbuilt.

Voice commands ("Foodia, dalej") and the "rescue protocol" menu (przesolone/przypalone quick-fixes) are 🔮 P3 — see 7's notes on wake-word detection cost/reliability before committing to this. **Worth weighing more seriously than a pure convenience feature once native platforms exist**: the Session 7 research frames voice-driven cooking navigation as a real accessibility gap, not just a nice-to-have — a "Read my recipe" dictation mode has direct value for cooks with visual or motor impairments, an underserved need today (`FUTURES.md` Section 3).

### 4.4 Micro-Cooperation & Comments 🎯 built (Session 3, moderation + "recognized" graduation added Session 13)

`NodeComment` (Section 3) is the real mechanism — reuses the exact "attach to a specific node, not the whole document" idea `2do` already validated for its own Comment/Content system, just scoped to `Ingredient`/`Step` instead of arbitrary Content types. **Built (Session 3):** `CommentComposer.svelte` (collapsed-by-default add form, public/private toggle, per ingredient/step), `CommentItem.svelte` (renders one comment, public ones get `ReactionButtons`), and `ReactionButtons.svelte` (the shared upvote/downvote widget — `lib/utils/reaction.ts`'s `applyReactionOverride` recomputes fresh from the untouched base `ReactionSummary` plus a component-local optimistic override every time, same discipline `2do`'s `ReactionModule` documents, never chaining overrides or mutating the base). Session-only, same honesty as everything else in this mock-era build — nothing persists past a reload; see `routes/recipes/[id]/+page.svelte`'s `sessionComments`. Substitutions now use the same `ReactionButtons` for their own votes, restructured out of the old "whole row is one button" markup so choosing a swap and voting on it are two independent controls, not one overloaded click target.

#### Comment moderation & substitution "recognized" graduation 🎯 built (Session 13)

Two features built together per explicit direction, closing both this section's own "deliberately not built" gap and Section 7 item 7 in one pass.

- **`UserRef.isModerator?: boolean`** (recipe.ts) — the one flag `/moderation` gates on. `piotr` (recipes.mock.ts) is the one fixture designated a moderator, arbitrarily chosen between the app's two existing identities — there's no role-granting UI in this mock-only app, same honesty every other role flag in this codebase already carries.
- **`lib/types/moderation.ts` / `lib/state/commentModeration.svelte.ts`** (this app's 7th `.svelte.ts` rune store) — a real report/review flow, reusing the exact "bad-actor report, reviewed by a moderator" shape `2do`'s own Report system already establishes, deliberately NOT its full 9-value `CommentStatus` enum (this app's comment model has no such states — a report/removed lifecycle lives entirely in this separate cross-route store, never mutating the loaded comment itself). A `CommentReport` denormalizes its own recipe/target context at report time (the reporting UI already has it on hand) — this is what lets `/moderation` render a useful queue without re-scanning the whole recipe corpus for context, the same "carry a label, avoid a lookup" convention `2do`'s own `Relationship.to.label` already establishes. Filing a report marks it `'pending'` but does **not** hide the comment — only an explicit moderator action (`resolve(id, 'remove')`) does, matching how real moderation review works (content stays visible while under review, not pre-emptively hidden on one unverified report).
- **`CommentItem.svelte`** gained an optional `context` prop (recipeId/recipeName/targetLabel — every real call site on `/recipes/[id]` passes it) — a public comment shows a "🚩 Zgłoś" toggle (revealing a reason picker: spam/abuse/unsafe/other) unless it already has a pending report (shown as a disabled "Zgłoszono" label instead); a comment a moderator has removed renders a tombstone ("Komentarz usunięty przez moderatora.") in place of its real content/author, the same "this used to be visible, here's why you can't see it now" idea `2do`'s own `ContentPlaceholder` already establishes, simplified to this app's own smaller scale.
- **`lib/utils/substitution.ts` gained `netReactionScore`/`RECOGNITION_THRESHOLD` (10)/`isEligibleForRecognition`**, and **`lib/state/substitutionModeration.svelte.ts`** (this app's 8th rune store) holds which substitution ids a moderator has actually promoted. **Crossing the threshold only makes a substitution ELIGIBLE — it does NOT itself grant the "⭐ Sprawdzone przez społeczność" badge**, which still needs an explicit `markRecognized` action — the same "explicit approval, not a silent vote-count auto-promotion" call `2do`'s own Session 30 "Spawn & Link" pattern already makes for its own analogous graduation, reused here rather than reinvented. `source: 'system'` substitutions are never eligible (already the curated/official option — "recognized" is specifically the community-earned-trust label). The badge is applied wherever a recognized substitution renders on `/recipes/[id]` — both the swap-picker row and the already-chosen-substitution display — and is inherently allergy-safe, since it's only ever applied to whatever already passed `filterSafeSubstitutions` before reaching either spot.
- **`/moderation`** (new route, `noindex`, not linked from the main nav — same "credential-gated internal tool" treatment `personali`'s own Admin Console gives its dashboard — reachable only via a "Moderacja" link inside `UserAvatarMenu`'s dropdown, shown only when `authStore.account?.isModerator`) — a purely client-side gate (`authStore.hydrated && authStore.account?.isModerator`), same reasoning `auth.svelte.ts`'s own header comment already gives for why nothing authentication-shaped lives in a server load in this app (no real backend, and the Capacitor build prerenders everything at build time regardless). Three sections: pending comment reports (Remove/Dismiss), substitutions that have crossed the threshold but aren't yet recognized (Mark as verified), and already-recognized substitutions (Undo). Scoped to the fixture corpus only (`mockApiClient.listDetails()`) — a substitution proposed live during the current tab session never accumulates real reactions anyway, since `ReactionButtons`' own vote override is a component-local display only, never aggregated anywhere shared, so there's nothing for a live-proposed substitution to become eligible FROM in this mock-era build; a real, stated scope boundary, not silently glossed over.
- **Verified** with a standalone 19-assertion logic-equivalent script (report → pending → dismiss round-trip leaving the comment visible throughout; report → pending → remove marking it removed; an unrelated comment staying untouched; the real fixture's own `s1` (net 11, community) correctly eligible while `s6` (net 5, community, the peanut-milk allergy-guardrail fixture) correctly is not; a system-sourced substitution never eligible regardless of score; eligibility alone not granting the badge; mark/unmark/idempotent-remark all behaving correctly) — all 19 passed. `npm run check`: 0 errors, same pre-existing warning set. Dev-server smoke test confirmed `/moderation` returns 200 in both languages, the report toggle renders on a real recipe page, and the recognized badge correctly does NOT show by default (nothing's been marked yet in a fresh session). Both build targets rebuilt clean, including confirming the Capacitor static output's prerendered `moderation.html` exists and renders the correct heading.
- **Deliberately still not built:** voting on a *private* note (meaningless — it's only ever visible to its author, `CommentItem.svelte`'s own guard); live re-sorting of substitutions as votes come in (`sortSubstitutionsByReaction` still only sorts once, from the untouched base data, at render time — re-sorting live would make rows jump under the viewer's cursor mid-click, a deliberate UX call, not an oversight); the identical "recognized" mechanism extended to `StepAlternative` (4.9) — the ask was specifically "substitution," kept scoped to that, though the exact same threshold/store shape would extend cleanly later. See Section 7's own new items for the rest.

### 4.5 Smart Pantry & E-Grocery 🎯 P1 (local pantry) + P2 aggregation/export — both built / 🧩 P2 (dedup, real e-grocery API partnership)

P1: a local, client-only `PantryItem[]` checklist (Section 3). **P2's aggregation, built Session 5:** `/shopping-list` cross-references the current week's `MealPlan` against the Pantry via `lib/utils/shoppingList.ts`'s `aggregateIngredients`/`crossReferencePantry` — same (name, unit) compound-key grouping discipline as the rest of this app's honesty culture: two recipes both needing "Czosnek" in the same unit sum correctly, but a pantry match in a *different* unit (e.g. needs `ml`, pantry has `l`) is never silently subtracted — it's shown at full needed quantity with a `partiallyCoveredDifferentUnit` flag instead, since unit conversion is ingredient-density-dependent (Section 7 item 3, ✅ **now solved — see 4.10 and Session 25**; that flag is gone, replaced by a real four-value `unitStatus`). A "Kupione → dodaj do spiżarni" button per missing item closes the loop by calling `pantryStore.add()` directly.

**Export:** exactly the brain-dump's own "architecturally ready, MVP can be simple" framing — `lib/utils/shoppingExport.ts`'s `copyToClipboard` (with a visible `<textarea readonly>` fallback for browsers/contexts where the Clipboard API isn't available) plus `exportToEGrocery`, the named integration point: today it's an honest stub that does the same clipboard copy and says so, returning a semantic result code the caller translates via `t()` (`'copied' | 'failed'` / `'stub-copied' | 'stub-failed'`, refactored Session 6 for the interface-language work — every call site already expects that shape, so swapping in a real Glovo/Frisco POST later touches only this one function's body).

✅ **Fixed (Session 12) — a real, small gap surfaced by the Session 7 research pass (`FUTURES.md` Section 1), independently confirming Foodia's own already-shipped aggregation logic is sound while flagging a genuine bug next to it:** `pantryStore.add()` (`lib/state/pantry.svelte.ts`) used to always append a new `PantryItem`, even when one with the same `(ingredientName, unit)` already existed — logging "Sól, 200g" twice produced two 200g rows instead of one 400g row, exactly the "phantom duplicate stock" failure mode the source research names as a top user complaint across competing apps. Now merges on that same `(name, unit)` compound key `shoppingList.ts`'s own `aggregateIngredients` already established (case-insensitive, trimmed) — matching quantities sum, `updatedAt` bumps; a different unit for the same ingredient name still stays a separate row, same "can't safely convert units" reason `crossReferencePantry` already states. Verified with a standalone 7-assertion logic-equivalent script (exact-duplicate merging, case/whitespace-insensitive matching, distinct units staying separate, distinct ingredients staying separate, blank-name no-op) plus `npm run check` (0 errors) and a dev-server smoke test on `/` and `/pantry`.

**One P2 candidate from the same research pass, still not built:** SKU-mapping for e-grocery (mapping an aggregated fractional need like "1.5 cups sour cream" onto real purchasable package sizes, not just a raw text line — genuinely needed once `exportToEGrocery` becomes a real integration, itself density/unit-conversion-adjacent work per Section 7 item 3), speced in `FUTURES.md` Section 1.

#### Auto-deduction — the loop's missing third leg 🎯 built (Session 28), closes `FUTURES.md` Section 1 item 4

Plan → shopping list → pantry was real and had been since Session 5. **Cook → pantry did not exist at all.** The only thing that ever took anything *out* of the pantry was `pantryStore.markUsed`, which deletes a whole row by hand — a checklist gesture, not a consequence of having cooked something. So the pantry drifted stale the moment anyone actually used it, and every shopping list computed from it drifted with it. Naming this "adjacent, not joined" was accurate: the two ends of the pipeline were wired, the loop wasn't closed.

- **`MealSlot.cookedAt?: string`** — the state this section has flagged as missing since Session 7 ("`MealSlot` has no 'cooked' state at all today"). A timestamp rather than a boolean, since "when" also answers "did I already make this on Tuesday" for free. Optional and needing **no migration**, unlike `MealSlot.id` (Session 23) or the plan's own identity (Session 24) — nothing reads it expecting a value.
- **`lib/utils/cookingDeduction.ts`** — pure, framework-agnostic, `densityFor` injected rather than imported, same discipline `shoppingList.ts`/`recipeFilter.ts` follow. It is the literal inverse of `crossReferencePantry`: that one asks "given what I have, what must I buy", this one asks "given what I just cooked, what did I spend" — deliberately running on the same `units.ts` engine and the same name-keyed matching, because two different answers to the same pantry question is exactly how a pantry feature stops being trusted (the argument `pantryStatus.ts` already makes for itself).
- **Three decisions worth stating, each rejecting a plausible alternative.** (1) **Not scaled by `MealSlot.servings`** — every other quantity in this app is un-prorated for want of a `baseServings` field, and here it's not merely consistency but correctness: the shopping list that filled this pantry summed un-prorated quantities, so a servings-scaled deduction would spend more than was ever bought and drive the pantry into a permanent invented deficit. (2) **Rows are spent oldest-first**, which is what a real pantry does. (3) **An ingredient with no pantry row at all is silent, not a shortfall** — the cook demonstrably had it, it was simply never logged; warning about every untracked ingredient would bury the one case `FUTURES.md` actually specced under noise about salt and pepper.
- **`pantryStore.consume` / `restoreConsumed`** — a real decrement, clamped at zero per row (a pantry reading "−150 g flour" is a worse lie than one reading 0, exactly the behavior `FUTURES.md` proposed for this case), with fully-spent rows dropped rather than left as 0-quantity ghosts. `consume` returns a before-snapshot of every row it touched so an undo can restore it **exactly**, including re-inserting a row that was emptied and removed — the same "give the caller something real to undo with" call `markUsed` already made in Session 24.
- **A preview the cook confirms, not the silent background write the spec asked for.** `FUTURES.md` says the deduction should happen "immediately, in the background"; this app's own house rule says never silently rewrite what a cook is looking at. Returning a *plan* rather than performing one satisfies both — the review screen lists every row that will change before anything is written, the write is one tap away, and the outcome screen offers a real undo. The two shortfall signals stay visually distinct exactly as `FUTURES.md` asked ("you may have been short on X" vs. the different, weaker "I can't tell how much you had", the latter reusing 4.10's own `needsDensity`/`incompatible` distinction rather than inventing a second vocabulary for it).
- **Deliberately asymmetric, and stated rather than papered over**: clearing a meal's "cooked" mark on `/plan` does **not** credit anything back to the pantry. The deduction is undoable from the finish screen, while the cook can still see exactly what was spent; a "wasn't cooked after all" tap days later has no idea what was deducted or what's been re-bought since, so crediting stock back there would be inventing pantry contents.

### 4.6 Internationalization & Content Translation 🎯 built (Session 6)

Two deliberately separate axes — same split `2do`'s own CLAUDE.md documents for the identical reason: a small, curated, developer-maintained set of **interface** strings vs. an unbounded, community-submitted set of **content** translations for user-generated recipe text. Conflating them would mean either forcing every recipe's translations through a fixed message catalog (nonsensical for user-generated data) or forcing UI chrome through a per-recipe translation workflow (overkill for "Dodaj"/"Add"). This section covers both halves, built together in one session since the content-translation UI's own "which language is the viewer currently in" question is answered directly by the interface layer.

#### Interface language (PL/EN)

No Paraglide/inlang dependency — a small, hand-rolled system, appropriately scoped for two languages and a few dozen keys (`2do`'s own compiler-based i18n tooling is real overkill at this size; revisit if the string count or locale count grows a lot).

- **`lib/i18n/messages.ts`** — flat, dot-namespaced keys (`'nav.plan'`, `'plan.slot.breakfast'`, ...), one `pl` object and one `en` object; `en` is checked against `pl`'s own key set via `satisfies Record<keyof typeof pl, string>`, so a missing English string is a **build-time type error**, not a silently-broken fallback discovered in production.
- **`lib/i18n/plural.ts`** — real CLDR-shaped pluralization: Polish genuinely has three cardinal forms (1; 2–4 excluding the 12–14 teens; everything else), English only two. `lib/i18n/t.ts`'s `tPlural(baseKey, n)` selects `.one`/`.few`/`.other` accordingly, falling back to `.other` for English's own `.few` entries (which are just a copy of `.other`, kept explicit rather than omitted so a missing-key fallback never masks a real typo elsewhere).
- **`lib/i18n/t.ts`**'s `t(key, vars?)` reads `uiLocaleStore.locale` (a rune getter) on every call — the same "plain function reads a reactive getter, reactivity flows through whatever calls it" pattern `2do` documents for its own `canViewingAs()`. Called directly inside template expressions or `$derived` (both tracked contexts), so the whole UI re-renders instantly on a language switch with zero extra wiring at each call site. Script-level arrays that carry translated labels (onboarding's `DIET_OPTIONS`/`GOAL_OPTIONS`/`HARDWARE_OPTIONS`, `/plan`'s `SLOT_LABEL`) had to become `$derived`, not a plain `const` — a `const` built once at component creation would go stale the instant the language changes.
- **SSR-correct locale resolution** — `hooks.server.ts` resolves the locale once per request (a `foodia-locale` cookie first, then the `Accept-Language` header, then the app's own default) and writes it into `event.locals.locale`; the root `+layout.server.ts` threads it into page data; `+layout.svelte` seeds `uiLocaleStore` from it in a plain top-level (not `$effect`-gated) statement, so the very first paint — server and client alike — already agrees on the right language, no flash. `app.html`'s `<html lang="%lang%">` placeholder is filled in by `hooks.server.ts`'s own `transformPageChunk`, the standard documented SvelteKit pattern for a dynamic `lang` attribute.
- **`LanguageSwitcher.svelte`** — mounted in **both** the navbar and the footer (a new `AppFooter.svelte`, which didn't exist before this session), as asked. Switching writes `uiLocaleStore` directly (instant, no reload, no server round-trip) and persists the choice via a cookie (`lib/utils/cookies.ts`, the same `document.cookie` SSR-guarded helper shape `2do`'s own `cookies.ts` establishes) so the *next* fresh page load starts server-rendered in the right language too.
- **Coverage**: every route (`/`, `/plan`, `/pantry`, `/onboarding`, `/shopping-list`, `/recipes/[id]`, the cooking-mode overlay) and every shared component (`CommentComposer`, `RecipeCard`'s hardware-match badge) migrated — verified by curling both `Accept-Language: en` and the default (no cookie) path against every route and grepping for the expected strings in each language, not just spot-checked.
- **One real correctness fix made along the way, not just a translation pass**: `lib/utils/shoppingExport.ts`'s `copyToClipboard`/`exportToEGrocery` used to return hardcoded Polish status strings directly. Refactored to return semantic result codes (`'copied' | 'failed'`, `'stub-copied' | 'stub-failed'`) instead — the presentation layer (`/shopping-list`) is what turns a code into text via `t()`, since the interface's own language can change at any moment and business logic shouldn't be baking in a display string.
- **Left open, deliberately smaller in scope than a real Settings-driven locale system:** no `/settings` page, no separate ranked content-language preference list — the content-translation resolver below reads the *current interface locale* directly as a single-entry hierarchy, not a multi-locale ranked preference the way `2do`'s own system has. A reasonable, smaller scope for this app's current size; worth revisiting if a real multi-locale audience emerges. See Section 7.

#### Community content translation (recipes)

The three explicit asks — a "view in original language" button, submitting alternatives/improvements to an *existing* translation, and proposing changes to the *original* content itself — turn out to be **one mechanism**, not three. A `Translation` (2's own type listing above) always names a `locale`; when that `locale` happens to equal the recipe's own `sourceLocale`, the submission is a same-language revision suggestion rather than a foreign-language translation — same shape, same submit form, same competing-votes resolution, distinguished only by a computed `isSameLocaleSuggestion` flag. This is a deliberate reuse, not a missing second feature — stated explicitly in `lib/utils/translations.ts`'s own header comment so a future session doesn't "fix" it by building a second, parallel suggestion system.

- **`lib/utils/translations.ts`** — pure, framework-agnostic functions (no Svelte import), same discipline `substitution.ts`/`hardware.ts`/`week.ts` already follow:
  - `getRecipeVersions(recipe, extra?)` — every selectable version: the true original, plus one entry per distinct locale with at least one `Translation` (competing submissions for the same locale collapse to the single highest-net-reaction one, ties broken by newest — same "the picker lists versions, not every competing row" simplification `2do`'s own multi-locale picker documents).
  - `resolveRecipeVersion(recipe, hierarchy, versionKey?, extra?)` — what to actually render. An explicit `versionKey` (a picker choice) wins outright, **including** a same-locale suggestion — the *only* way one is ever shown. Without an explicit pick, walks `hierarchy` (today always `[uiLocaleStore.locale]`): a locale equal to the recipe's own `sourceLocale` **always** resolves to the true original, full stop — a same-locale suggestion is never auto-substituted for what the author actually wrote, regardless of its reaction score. This was verified with a real, deliberately-adversarial fixture (see below), not just asserted in a comment.
- **`SuggestTranslationModal.svelte`** — one form for both cases. Locale picker (`COMMON_CONTENT_LOCALES`: pl/en/de/fr/es/uk, plus a free-text "other" option — a recipe can be translated into a language the *interface* doesn't support yet, a deliberately wider vocabulary than `UiLocale`). Textareas are pre-filled from the **best already-submitted text for the chosen locale** (so improving an existing translation starts from what's actually there, not from blind original-language text the submitter may not even read) — but the submitted `fields` are diffed against the **raw original**, not the prefilled text. This distinction is load-bearing, not pedantic: a `Translation` is a complete, independent candidate that fully replaces the original's fields wherever present, so a one-field tweak to an already-translated recipe must still carry every other field that was previously translated, or it would silently regress them back to the original the moment this new submission out-votes the old one.
- **`TranslationBadge.svelte`** — reuses this app's existing `<details>`-based dropdown idiom (already used twice — the ingredient swap list, the shopping list's "show as text") rather than introducing a new popover component. Shows a "View Original" button whenever *not* currently viewing the original, plus a version-picker `<details>` whenever more than one alternative exists.
- **A real bug caught during design, not shipped**: the recipe detail page's own "View Original" click handler originally converted the picker's `'original'` key to `versionKey = null` before passing it to the resolver — which seemed equivalent, but isn't: with `null`, the resolver falls through to its normal hierarchy walk, which (if the interface is in English and a good English translation exists) immediately re-resolves back to that translation, silently undoing the click. Fixed by passing `'original'` straight through so the resolver's own explicit-key branch (which always returns the true original for that key) actually runs. Caught by a standalone logic-verification script exercising this exact scenario before it ever reached the browser, not discovered by accident.
- **`recipesById.r1` (Spaghetti Bolognese)** carries the real showcase fixture: `tr1`, a well-reacted English translation covering all three fields; `tr2`, a **same-locale, net-negative-reaction** suggestion — deliberately unpopular, to prove the resolver's own "never auto-applied regardless of reactions" rule actually holds, not just for a hypothetical positive case.
- **Scope, stated plainly**: only `name`/`summary`/`description` are translatable (matches `2do`'s own exact `TranslatableField` scope) — ingredient names and step text are **not** translatable in this pass. Viewing a recipe in a translated language still shows the ingredients list and steps in the original Polish. A known, flagged gap, not an oversight — see Section 7.

### 4.7 Search, Filtering & Categorization 🎯 built (Session 12) — speced Session 7 from real research findings

Foodia had **no search or filter UI at all** — the home feed applied only the hardware hard-filter (`ownsRequiredEquipment`, 4.1). `RecipeCard.tags`/`dietFlags` already existed as real fields (Section 3) but — a correction to this section's own original claim — `dietFlags` was never actually *rendered* anywhere before this session either, only `tags` was; both are shown on `RecipeCard.svelte` now (`dietFlags` gets its own distinctly-colored pill row, above the plain `tags` row). Of every idea surfaced by the Session 7 research pass (a 47-Reddit-thread competitive analysis of Paprika, MyFitnessPal, Mealime, Yazio, Cronometer, and Samsung Food — see `FUTURES.md` for the full deep-dive), this was the single most "pull-forward-able": the data model was already there, only the UI and the correct filtering logic were missing.

**The specific, named failure mode this was built to avoid, taken directly from the source research (Paprika named specifically):** multi-tag filtering that silently applies logical **OR** where the user expects **AND**. A cook filtering by "Vietnamese cuisine" *and* "salads," expecting the intersection (only Vietnamese salads), instead gets flooded with every Vietnamese dish (heavy Pho soups included) *plus* every salad in the whole corpus (Greek, Italian, everything) — the union. This makes tag filtering functionally useless the moment a collection passes a few hundred recipes, and was explicitly named as one of the most common, specific engineering complaints across the source Reddit threads.

**`lib/utils/recipeFilter.ts`** — pure, framework-agnostic functions (no Svelte import), same discipline `substitution.ts`/`hardware.ts`/`week.ts`/`shoppingList.ts` already follow:
- `RecipeFilters` carries two independent facet groups (`tags`, `dietFlags`), each with its own `included: string[]`, `excluded: string[]`, and `mode: 'and' | 'or'`. An empty `included` array means "unrestricted," same convention `2do`'s own `SearchFilters` already uses for its array-typed facets.
- `matchesFacet` — **AND (every included value must be present) is the default**, exactly the fix for the Paprika bug above; `OR` (any included value present) is only ever reached via an explicit per-facet toggle, never a default.
- **Exclusion, implemented as ONE cycling control per value, not two separate multi-select lists.** The spec's own wording ("a second multi-select for 'avoid these tags'") named two lists; the actual choice made was a single pill per tag that cycles `neutral → include → exclude → neutral` on click (`cycleFacetValue`) — functionally the same real, click-driven exclusion control (never a `-tag` query-string operator, matching `2do`'s own deliberate "no Power Query parsing" restraint), just one button per value instead of two, and `included`/`excluded` are kept mutually exclusive by construction. Exclusion itself has no AND/OR mode — "reject if ANY excluded value is present" is the only sensible semantic (`matchesExclusion`), the Paprika bug was specifically about *inclusion* combining wrong, not exclusion.
- **The two facet groups (tags, dietFlags) always combine via AND with each other** — a recipe must satisfy the tag facet AND the diet-flag facet — the standard two-level faceted-search shape `2do`'s own `SearchFiltersSidebar` already establishes, just scoped to the two facets this app actually has.
- `distinctValues` derives the option list from the real corpus (not a fixed vocabulary — `tags`/`dietFlags` are free text, Section 3's own "no fixed vocabulary yet" note), the same "no fixed list, derive from what's actually there" call `personali`'s own `distinctCollaborationModes` already makes for an analogous free-text field. Options are computed from the FULL, unfiltered corpus and don't shrink as other filters are applied — a simpler choice than faceted counts, matching `2do`'s own facet pickers.

**`FacetFilterPanel.svelte`** (`lib/components/search/`) — one reusable panel for both facet groups (a heading, an AND/OR segmented toggle, and the cycling pill row), rather than two near-identical components. Mounted twice from `routes/+page.svelte`, inside a collapsed-by-default `<details>` (this app's own existing disclosure idiom — already used by `TranslationBadge`, the ingredient swap list, the shopping list's "show as text") labeled with an active-filter-count badge (`tPlural('filters.activeCount', n)`, real CLDR-plural Polish, same convention `home.hiddenNote` already established) so the feature stays discoverable even collapsed.

**Applied AFTER the existing hardware hard-filter, never instead of it** — `routes/+page.svelte`'s own `visibleRecipes` is `filterRecipes(cookableRecipes, filters)`, so a recipe hidden for lacking equipment stays hidden regardless of what's selected here. Two distinct empty states, not one conflated message: `cookableRecipes.length === 0` still shows the original hardware-specific `home.empty` copy (unrelated to filtering); `cookableRecipes.length > 0 && visibleRecipes.length === 0` shows a new `filters.noMatches` message with an inline "Clear filters" button — the two causes of "nothing to show" are now told apart, not merged into the pre-existing hardware-only message the way they would have been left otherwise.

**Verified** with a standalone 11-assertion logic-equivalent script covering: the literal Paprika-bug scenario (AND-by-default returns only the true intersection, never the union), the same two tags under an explicit OR toggle correctly returning the union instead, exclusion dropping every recipe carrying the excluded tag regardless of mode, case-insensitive matching, the two facet groups combining via AND with each other (a recipe passing the tag facet alone is still correctly rejected if it fails the diet-flag facet), empty filters passing everything through unrestricted, `distinctValues` deduping/sorting correctly, and `cycleFacetValue`'s full neutral→include→exclude→neutral cycle staying mutually exclusive at every step — all 11 passed. `npm run check` clean (0 errors, same pre-existing warning set). Dev-server smoke test confirmed the panel and every real fixture tag/dietFlag value render server-side in both `pl` and `en`. Both build targets (`npm run build`/`npm run build:capacitor`) rebuilt clean.

**Deliberately not in this pass:** micronutrient-level filtering (added vs. natural sugars, specific allergen combinations beyond tag exclusion) — that needs `MacroSummary` to carry a real nutritional breakdown, which itself needs a real nutrition database, an already-open, unaddressed gap (Section 3). This report sharpens *why* that gap matters (diabetics tracking glycemic impact, not just an abstract accuracy concern) without changing the fact that it's still blocked on the same precursor. See `FUTURES.md` Section 5 for the full finding. Also not built: full-text/query search (a name/description search box) — this pass only covers structural tag/dietFlag filtering, matching the spec's own scope exactly.

### 4.9 Device/Equipment Alternatives 🎯 built (Session 9) — resolves 4.1's own long-flagged "temporarily disable broken equipment" gap

New module, not in the original brain-dump by this name — the step-level mirror of Ingredient Alternatives (4.2), built to close a gap 4.1 has flagged since the very first pass of this document: a recipe's `requiredEquipment` (Card-level) is a hard, whole-recipe filter that hides a recipe outright if the cook doesn't own an airfryer, but nothing existed for the much more common real case — a recipe the cook mostly *can* make, where just **one step** assumes equipment they don't have. ### 4.10 Real Unit Conversion 🎯 built (Session 25) — resolves Section 7 item 3, open since the first pass of this document

The gap this closes was stated in the very first version of Section 3 ("unit-conversion tables — `cup` → `g` is ingredient-density-dependent, not a fixed ratio") and re-flagged by every feature that ran into it since: `crossReferencePantry` (Session 5) couldn't subtract a pantry row in a different unit, `pantryStore.add()` (Session 12) had to fork a separate row per unit, `FUTURES.md`'s SKU-mapping idea was blocked on it, and 6.5 proposed solving it with an LLM. **None of that was necessary.** The framing that kept it open for 24 sessions was a false binary — either license a real per-ingredient density database, or don't convert at all.

**The actual decomposition: two genuinely different problems, not one** (`lib/types/units.ts` states this in its own header, so a future session doesn't re-merge them):

1. **Same-family conversion** (g↔kg↔oz↔lb, ml↔l↔cup↔tbsp↔tsp) is exact arithmetic against fixed, internationally standardized factors — true regardless of what's being measured. **No density is needed, ever, and none is consulted** — `convertQuantity` ignores a supplied density entirely on this path (asserted directly, not just intended). This alone covers most real mismatches this app actually sees.
2. **Cross-family conversion** (cup→g) genuinely does depend on the ingredient. The third option neither prior framing considered: **ask the cook, once.** `DensityClass` is five broad, honestly-labeled classes with real representative reference points — `powdery` 0.53 (flour, cocoa), `granular` 0.85 (sugar, rice), `liquid` 1.0 (water, milk, oil), `light` 0.35 (rolled oats, shredded cheese), `dense` 1.2 (honey, peanut butter). Not lab-precise for any specific ingredient, and never presented as more than that — good enough for a shopping list, which is the only thing it's used for.

- **`lib/utils/units.ts`** — pure, framework-agnostic (same discipline `shoppingList.ts`/`substitution.ts`/`recipeFilter.ts` already follow). `normalizeUnit` collapses every spelling this app's own real content actually uses ("Tbsp"/"tbsp"/"tbsp."/"tablespoons" → one unit — a real problem Session 24's Budget Bytes import created, where a naive `(name, unit)` key silently fragmented one ingredient into three); `familyOf`; `convertQuantity` (returns `null` rather than guessing whenever real math can't bridge two units); `formatQuantity` (conversion math is the first thing in this app that can produce `263.411764…`, so every quantity the UI or the clipboard export renders now passes through this).
- **`lib/state/ingredientDensity.svelte.ts`** — this app's 9th `.svelte.ts` rune store, `localStorage`-backed with the same lazy-hydrate discipline as `pantry`/`mealPlan` (for the same SSR-mismatch reason). Keyed by normalized ingredient name. **This cache is what makes "ask" viable rather than annoying**: without it the same question would resurface on every shopping list, which is exactly what would have made this worse than not converting.
- **`crossReferencePantry` gained a real four-value `unitStatus`**, replacing the old binary `partiallyCoveredDifferentUnit` flag: `match` (same unit, straight subtraction), `converted` (real math resolved it — `pantryQuantity` is the converted number), `needsDensity` (a genuine cross-family mismatch with no class cached — a real, *answerable* question), and `incompatible` (an `'other'`-family unit like "ząbki"/"clove" on either side — no density could ever bridge these, the same honest dead end the old flag represented, now correctly distinguished from the answerable case). `densityFor` is **injected**, not imported — this file stays a pure function, the caller passes `ingredientDensityStore.classFor` in. **`needsDensity` deliberately outranks a successful conversion**: a pantry can hold both a convertible row and an unresolved one for the same ingredient ("500 g flour" plus "2 cup flour"), and reporting `converted` there would quietly drop the cup row from the subtraction *and* never ask the one question that would recover it.
- **The prompt lives on `/shopping-list` only, not in `pantryStore.add()`** — a real placement call, not an omission. The shopping list is where an unresolved mismatch actually blocks a decision ("do I need to buy flour or not?"); adding to the pantry doesn't, so `add()` merges wherever real math already allows (including same-family, which it never could before, and spelling variants, which used to fork a phantom row) and otherwise just keeps a separate row, exactly as it always did. No modal ever interrupts logging groceries.
- **Verified** — `scripts/verify-units.ts`, **48 assertions, all passing**, and unlike most prior sessions' verification scripts this one **imports the real modules** rather than mirroring them (`units.ts`'s only non-relative import is `import type`, erased by esbuild; `shoppingList.ts`'s `$lib` value imports resolve through `.svelte-kit/tsconfig.json`'s `paths`, which tsx reads) — so these run against exactly the code the app ships, not a copy that can drift. Only `pantryStore.add()` is mirrored, and is labeled as such, since a rune store can't be evaluated under plain tsx. Coverage includes the literal claim Section 7 item 3 made for 24 sessions (1 cup flour ≈ 125 g vs. 1 cup honey ≈ 284 g, *and* that the two genuinely differ), density never being consulted on the same-family path, `'other'`-family units returning `null` even with a density supplied, cross-family round-tripping back to itself, all four `unitStatus` values, multiple pantry rows summing, and the `needsDensity`-outranks-`converted` precedence case in both directions.
- **Verified live in a real browser too**, not just by script — a real week's plan against a deliberately-constructed pantry exercising all four statuses at once on one list: Passata (`match`, fully covered), Mięso 0.2 kg against a 400 g need (`converted` → exactly 200 g still missing), Czosnek in g against a "ząbki" need (`incompatible`, honest badge), Spaghetti in cups against a g need (`needsDensity` → the prompt, and only that one item). Answering it ("Ziarnisty") moved Spaghetti to fully-covered at 402.2 g in the same tick, the class persisted to `localStorage`, and a full page reload did **not** re-ask. Zero page errors; the clipboard export text carries clean quantities, no float noise.
- **Deliberately not built**: no per-ingredient density override (the five classes are the whole vocabulary — a real per-ingredient figure is what this section's own framing argues *isn't* needed for a shopping list); no way to change an answer once given (a real, small follow-up — the store has `classify` but nothing surfaces a "that was wrong" control yet); recipe-level display conversion (viewing a recipe's own ingredients in your preferred unit system) is untouched — this pass covers Pantry/shopping-list reconciliation only, which is where the ambiguity actually blocked something.

### 4.11 The Tabular Recipe View 🎯 built (Session 27) — the default view at the top of every recipe

The source is a screenshot the founder sent: *"i can't believe someone solved recipe design decades ago and everyone just decided to ignore it"* — the Cooking for Engineers table (2006). Ingredients as rows down the left, each operation as ONE cell bracketing every row it consumes, so the SHAPE of a dish is legible before reading a word of prose: what goes in with what, and at which point things stop being separate things.

**It needed no new recipe data.** `Step.ingredientIds` has been in this app's type since Section 3 was first written, and until now only Cooking Mode's per-step highlight ever read it. The table is what that field was always for.

- **`lib/utils/recipeMatrix.ts`** — pure, framework-agnostic (same discipline `units.ts`/`shoppingList.ts`/`recipeFilter.ts` follow). `buildRecipeMatrix` groups each ingredient under the FIRST step that names it, which is what makes every operation's row range contiguous — the property the whole layout depends on. `layoutRecipeMatrix` turns that into placed CSS-grid cells, so the component does no arithmetic of its own and the geometry is verifiable without a browser.
- **The one structural assumption, stated rather than discovered later: a recipe is treated as a LINEAR chain** — each operation folds the previous one's output together with whatever it names for the first time. That is exactly what `Step[]` encodes; there is no parent/branch field to read a real tree out of. A genuinely parallel recipe (boil the pasta while the sauce reduces) renders as a chain — visually a simplification, never a false claim about which ingredients an operation touches. Real branches need a `Step.dependsOnStepIds` that doesn't exist; inferring one from step text would be worse than the honest chain.
- **Leading steps that name no ingredient become full-width banner rows** above the table — "preheat the oven", "put a pan of salted water on". They're setup, not an operation performed on any row. A no-ingredient step in the MIDDLE stays a normal cell, because it really does act on the running preparation.
- **The empty areas under a finished operation are real merged cells** (`kind: 'filler'`), not holes. Looking closely at the original settles a question the layout can't decide by feel: it is a merged-cell TABLE with one uniform ingredient column, not a nested bracket diagram whose rows grow wider as the chain deepens. An empty grid area draws no borders, so without those cells the table loses the line under "melt" the moment the next operation starts.
- **Cell labels are DERIVED, not stored** (`terseStepLabel`: first clause, length-capped). A real `Step.shortLabel` field is the proper fix, but adding one leaves every existing recipe — fixtures and the 77 D1 rows alike — with an empty label until somebody re-authors it, so the layout would ship broken for all existing content. Deriving works for every recipe that already exists, in any language, with no migration. Tapping a cell shows the full sentence.
- **Ingredients no step names are reported, not hidden** — a real authoring gap the cook should be able to see, rather than one this layout papers over by folding them into a step that never claimed them.
- **Each row carries the pantry answer** (✓ / ◐ / ?) resolved through the same `crossReferencePantry` `/shopping-list` uses, so a tick here means exactly what a covered row means there. `unresolved` shows a question mark, never a tick — "I can't tell how much you have" is a different answer from either yes or no (4.10).

### 4.12 The Ingredient Sheet 🎯 built (Session 27)

Touching an ingredient anywhere on a recipe opens everything that ingredient IS to this cook, in one place: what it swaps for, what people have said about it, what it looked like, where it came from, whether it's already in the pantry, and how to get the recipe onto the week's plan.

- **Four tabs, opening on Pantry** — the first question anyone has about a specific ingredient, far more often than any other, is whether they need to buy it. Real coverage, the matching pantry rows shown as-is, the density question asked inline when it's the thing blocking an answer, and an add form seeded with what's actually missing rather than what the recipe asks for.
- **Everything per-ingredient moved here, and did NOT stay behind as well.** The swap picker, propose-a-swap, the ingredient's comment thread and its composer, and each swap's own discussion all used to render inline under every ingredient on the recipe page. Keeping both would mean two swap pickers on one page that can disagree — and inline-everything is what made this page render the same login prompt 22 times (Session 22's own note). What remains below the table is the canonical, linear, printable ingredient list the table is a summary OF, with a marks column and a tap target.
- **A swap chosen in the sheet changes the row in the table behind it**, because the page owns `chosenSubstitutions` and both views read it. The sheet decides nothing about the recipe; it is a lens onto state that lives one level up. It also never filters substitutions — the allergy guardrail (4.1) is applied by the page before the list reaches it, so this component is structurally incapable of showing an unsafe swap.
- **"Add to my planner" is the shopping-list loop said out loud**: adding the recipe to a plan is what makes the list ask for everything it needs and nothing already owned. Two weeks only (this and next) rather than a date picker — that's the realistic range for deciding to cook something you're looking at right now, and `/plan` is one link away.

### 4.13 Photos & Stories on a node 🎯 built (Session 27)

`comments.image_url` and `comments.kind` (`'note' | 'story'`, migration `0003`) — two columns on the existing table, not two new tables. A photo of what the ingredient actually looked like and the story of where it came from are both "somebody said something about this node": they already need everything a comment has (an author, a target, a timestamp, reactions, reporting, moderator removal). A parallel `ingredient_photos` table would have had to re-earn all of it, and would have left a photo **un-reportable**, which is not a corner an app accepting real uploads can afford.

- **`image_url` holds a `/api/media/[key]` path from the R2 route built in Session 26 — validated server-side, never trusted.** An arbitrary URL would turn every thread into an off-site embed (a tracking pixel, a hotlink, something this app can't take down when it's reported), which is exactly what the private-bucket/one-way-in design in `wrangler.jsonc` exists to prevent.
- **A moderator removal takes the photo with the text.** `toNodeComment` blanks both at the server boundary — leaving the image would render it directly under a tombstone saying the comment is gone.
- **A photo with no caption is a complete contribution** ("here's what mine looked like"), so `createComment` now requires text OR an image rather than text specifically, and the submit button agrees with the server instead of refusing what the server would accept.
- **Both are opt-in per call site** (`allowMedia`/`allowStory`, default off). `CommentComposer` renders under every ingredient, step, substitution and step-alternative on the recipe page; a file picker and a story toggle under all of them would bury the thing people came to do.
