# Foodia — Futures & Deep-Dive Research

**Status:** a companion document to `CLAUDE.md`, not a chronological session log. This is a synthesized, extended version of a market/user-research deep-dive the founder brought in — a competitive analysis of Paprika, MyFitnessPal, Mealime, Yazio, Cronometer, and Samsung Food (formerly Whisk), grounded in **47 real Reddit threads** from active users of those apps, not speculation (full citation list — thread titles, subreddits, dates — lives in the source PDF, *"Nowe Funkcjonalności Portalu Żywieniowego"*, if a specific claim needs verifying against its original source).

**Nothing below is phased into `CLAUDE.md`'s own 🎯 P1 / 🧩 P2 / 🔮 P3 buckets** — that's a founder call, not something this document presumes to make on its own. A handful of the report's *smaller* findings turned out to be natural, low-complexity extensions of modules Foodia already has, and those were folded directly into `CLAUDE.md` instead of duplicated here — each section below says explicitly where that happened and points back to the relevant `CLAUDE.md` section.

**How to read this:** each section states the finding (condensed and translated from the source report), how it connects to Foodia's own existing architecture where a real connection exists, what a concretely-Foodia-shaped feature under it would actually look like (not just the report's own abstract framing), and — where I have one — an extension, caution, or connection to Foodia's own existing code that the source report itself didn't raise. Genuinely founder-call items are marked ❓, matching `CLAUDE.md`'s own convention.

## 1. Smart Pantry 2.0 — the gap between "logged" and "true" inventory

**The findings.** Shopping-list algorithms in most competing apps are purely additive — they sum ingredient needs across recipes and almost completely ignore the pantry's actual state, treating "virtual pantry" and "shopping list" as disconnected silos. Concretely, three failure modes keep recurring across the Reddit threads:

- **No deduplication on manual entry.** Confirming a purchase and tapping "add to pantry" doesn't merge with an existing entry — users report their pantry filling up with a dozen duplicate "salt," "pepper," "olive oil" rows over months, at which point the app's own "you already have this" logic (which reads that phantom stock) starts wrongly suppressing real needs from the shopping list.
- **No unit consolidation.** If two recipes in a plan each need "1 tbsp butter" (one salted, one unsalted), the shopping list shows two separate fractional line items instead of suggesting one standard butter block with a note about self-dosing the salt.
- **No SKU-mapping for e-grocery integration.** When a week's plan aggregates to needing 1.5 cups (~350ml) of sour cream across three recipes, an e-grocery API integration typically maps that to a single standard 200ml package — silently under-buying, because the system never reasons about real purchasable package sizes vs. the abstract fractional amount a recipe算 needs.
- **Barcode scanning is scoped too narrowly.** Where it exists at all, it's built for *calorie lookup* (MyFitnessPal, Cronometer), never for *pantry logistics* — users want scanning an empty, discarded package to auto-increment that item on the next shopping list, and scanning a newly-bought item to auto-update pantry stock **and** deduplicate against what's already logged.
- **No auto-deduction.** Confirming a planned meal was actually cooked should immediately, in the background, subtract the used ingredient quantities from the virtual pantry — keeping the system continuously synchronized instead of drifting stale.

**Where Foodia already stands — better than the baseline, on one axis.** Worth stating plainly: the report's central "blind planning" critique (shopping lists computed by pure summation, ignoring the pantry) is **already solved** by Foodia's own Session 5 work. `lib/utils/shoppingList.ts`'s `crossReferencePantry` does real subtraction (`neededQuantity - pantryQuantity`), not blind summation, and honestly flags rather than fakes the case where a pantry match exists in a different unit (`partiallyCoveredDifferentUnit`, `CLAUDE.md` 4.5). This report is independent, external validation that Session 5's design was the right one — a genuine confidence-building data point, not just a self-assessment.

**What's still a real gap, mapped onto Foodia's own code:**

1. ~~**Pantry deduplication doesn't exist.**~~ ✅ **Fixed, Session 12.** `lib/state/pantry.svelte.ts`'s `add()` used to always append a new `PantryItem` — adding "Sól, 200g" twice produced two 200g rows, not one 400g row. Now merges on `(ingredientName, unit)` case-insensitively, summing `quantity`, genuinely the closest thing in this whole report to a one-line bug fix rather than a new feature. **See `CLAUDE.md` 4.5 for the actual implementation/verification detail.**
2. **SKU-mapping for e-grocery is a real, nontrivial requirement once a real Glovo/Frisco API exists** — `lib/utils/shoppingExport.ts`'s `exportToEGrocery` is an honest stub today specifically because there's no real integration to map against yet; when one exists, "1.5 cups sour cream" → "1 × 500ml carton" is genuine unit-conversion-adjacent work (the same ingredient-density problem `CLAUDE.md` Section 7 item 3 already flags as unsolved), not a trivial mapping table.
3. **Barcode scanning already has a home** — `CLAUDE.md` 6.1's own Capacitor "to finish the native wrap" list already names `@capacitor/camera` for Pantry barcode scanning as a P2 candidate. This report gives it concrete UX shape it didn't have before: scan-out (discarded packaging → increments shopping list) and scan-in (new groceries → updates + dedupes pantry) are two distinct flows, not one generic "scan a barcode" button.
4. **Auto-deduction is genuinely new** — `MealSlot` (in `lib/types/pantry.ts`) has no "cooked" state at all today, only an assignment. A real, mock-first-buildable feature: add a way to mark a planned meal as cooked (a `cooked?: boolean` on `MealSlot`, or a separate append-only cooked-log if a history matters more than a toggle), and on that action, decrement matching `PantryItem` quantities by the recipe's ingredient amounts — the exact inverse operation `aggregateIngredients` already performs in the other direction. This is the single most "shaped like Foodia already thinks" idea in the whole report: `/plan` and `/pantry` already have the connective tissue (`shoppingList.ts`) to support it.

**My own extension, not in the source report:** what happens when auto-deduction would take a pantry quantity negative (recipe needs 400g flour, pantry only has 200g logged)? The report doesn't address this. Given Foodia's own established honesty culture (never silently fake a number), the right behavior is: clamp the pantry quantity at zero and surface a distinct "you may have been short on {ingredient}" note — this is a genuinely different signal from the *pre-cook* "missing items" list (`/shopping-list`), since it's discovered only *after* the fact, when the plan's own assumptions about pantry stock turn out to have been wrong. Worth keeping these two signals visually distinct if built, not merged into one generic "problem" banner.

## 2. Reverse Meal Planning & the Zero-Waste Loop

**The findings.** "Leftover utilization" tools (Supercook is named specifically) are shallow — a simple ingredient-match search, not full-dish optimization: telling it you have onion, milk, and celery returns hundreds of results that merely *contain* onion, ignoring the actual goal of building a complete dish mostly from what's on hand. The report proposes **Reverse Meal Planning**: instead of starting from "what do I feel like eating," start from hard, dated pantry facts ("400g ground meat expiring tomorrow, half a bag of spinach") and search the user's own cooking history for recipes that maximize overlap with that critical ingredient set. A related, rarer-discussed failure is the **lack of horizontal planning**: a recipe needing a small non-standard amount (2oz of bourbon, a pinch of an exotic spice, 1/5 of a cabbage head) tells you to buy the whole product but never manages what happens to the other 80–95% — the report calls the fix **cascading recipe suggestion / "loop closing"**: after adding a recipe that uses 1/5 of a cabbage, the app should proactively suggest coleslaw or braised-cabbage recipes for the following days, driving the effective cost-per-serving down before the rest spoils. Current apps also don't estimate or optimize cost-per-serving at all.

**Connecting this to Foodia's own code.** This extends both the Pantry (`PantryItem` has no expiry concept — only `quantity`/`unit`/`updatedAt`) and `/plan`'s own `quickFill()` function (Session 4's plain round-robin, `routes/plan/+page.svelte`).

- **Reverse-plan mode**: `PantryItem` would need an optional `expiresAt?: string` (ISO date) — a real, small type addition. Start with manual entry (the user types an expiry when logging an item) rather than inferring shelf-life per ingredient category automatically, since the latter is its own density-table-shaped problem (the same *kind* of unsolved gap `CLAUDE.md` Section 7 item 3 already flags for unit conversion — flagging honestly rather than promising an automatic version up front). A "Reverse Plan" toggle on `/plan` would rank `availableRecipes` by how many ingredients match soon-expiring pantry items, as an alternative mode alongside (not replacing) the existing budget-constrained quick-fill.
- **Loop-closing / cascading suggestions**: this is genuinely tractable *without* AI, using data `aggregateIngredients` (`lib/utils/shoppingList.ts`) already computes. After a plan is assembled, a simple, deterministic, explainable rule: for any ingredient appearing in only **one** recipe's needed amount across the whole week, but which is realistically sold in a larger package (worth a small curated list of "bulk-only" ingredients — spices, alcohol, whole cabbages/melons, etc. — rather than trying to infer package size for everything), surface a "you'll likely have leftover {ingredient} — see recipes using it?" nudge, linking to a tag/ingredient-filtered view. This mirrors the same restraint `/plan`'s own quick-fill already demonstrates: a plain, deterministic rule, honestly *not* AI, labeled as such if built — matching this app's own established discipline (`CLAUDE.md` 6.2's own "the button must never be mistaken for the LLM-driven one").
- **Cost-per-serving**: `RecipeCard.costEstimate` already exists (whole-recipe cost) — cost *per serving* needs the already-independently-flagged missing `baseServings` field (`CLAUDE.md` build log, Sessions 4–5, `lib/utils/shoppingList.ts`'s own header comment). This report is a second, external, independent identification of that exact gap, for a genuinely different reason (waste-driven cost optimization, not just budget-bar arithmetic) — worth treating as a real priority signal, not a duplicate flag to ignore.

## 3. In-Cooking UX, beyond Wake Lock and Timers

**The findings.** The single most common complaint on cooking forums is the archaic separation of "Ingredients" and "Instructions" into two sections, forcing constant scrolling back and forth to check an exact gram amount at a critical, time-pressured moment (deglazing a hot pan) — made worse by the fact that touching a screen with flour- or grease-covered hands is a real physical barrier, and the screen may have already dimmed. The proposed fix is **hybrid/inline instructions**: instead of "Add previously prepared flour, sugar and salt," the step text itself should show "Add **200g flour**, **50g sugar** and **1 tsp salt**" with the amounts bolded directly inline, parsed and rendered live rather than requiring a second glance at a separate list. A related, smaller gap: no way to group ingredients by sub-recipe ("for the sauce" vs. "for the marinade") during mise-en-place prep. Beyond that: strong, explicit demand for **touchless interaction and voice control** — a "Read my recipe" dictation mode that reads out steps and advances on a spoken "next step" command — which the report frames not just as convenience but as a genuine **accessibility** gap: voice-navigable cooking apps would materially help people with visual or motor impairments maintain independent living, an underserved need today. Finally, **inline tutorials**: hyperlinked jargon ("make a roux," "sweat the onion") that opens a short, contextual overlay (a looping GIF or a text pill) instead of forcing the cook to leave the app for an external tutorial video, breaking workflow continuity.

**Where Foodia already stands.** `CLAUDE.md` 4.3 (Cooking Mode) already ships Wake Lock and inline timers as real, built P1 features — this report is independent validation that both were the right P1 scope, not just an internal judgment call. Voice commands were already correctly scoped as 🔮 P3 (`CLAUDE.md` 4.3/Section 7 item 10, "wake-word detection cost/reliability... needs its own feasibility pass"); this report adds a real, concrete reason to actually prioritize it once native platforms exist — the accessibility framing — worth folding into that existing note. **Done directly in `CLAUDE.md`,** not left here.

**What's genuinely new here, and buildable mock-first today:**

- **Hybrid inline instructions.** `Step.text` is currently a plain string. The cleanest implementation ties directly into data Foodia already has: rather than re-parsing free text for numbers (fragile, and duplicates a source of truth), author step text with a lightweight reference syntax pointing at real `Ingredient` fields (e.g. a step referencing `i1`'s `quantity`/`unit`), and have `CookingMode.svelte` interpolate + bold at render time. This means the amounts shown in a step are *always* consistent with the ingredient list, by construction, not by editorial diligence.
- **My own extension, not in the source report:** this idea directly exposes a real, currently-unaddressed inconsistency in a feature Foodia **already has**. When a user picks a substitution on the recipe detail page (`chosenSubstitutions`, `routes/recipes/[id]/+page.svelte`), only the ingredients list and the macro totals update — `CookingMode.svelte`'s own step text never reflects the swap. A cook who substituted lentils for ground meat still reads "Add mięso mielone, smaż aż się zrumieni" in Cooking Mode. Building hybrid inline instructions the way described above would fix this *automatically*, since the step's ingredient reference would resolve to whichever substitution is currently active. Worth flagging as a genuine, concrete bug/gap surfaced by thinking through this report's own idea, not just a speculative future nicety.
- **Ingredient sub-grouping.** `Ingredient` has no `group?: string` field today. A trivial addition, rendered as sub-headings ("Do sosu" / "Do marynaty") in the ingredients list.
- **Inline tutorials/glossary.** A real, medium-sized feature: a small curated dictionary (term → short explanation, maybe a GIF), triggered by tapping a highlighted term in recipe text. Buildable mock-first (a static dictionary + a tap-to-reveal popover, similar in shape to `TranslationBadge.svelte`'s own `<details>`-based disclosure pattern from Session 6) — but the actual *content* (writing good, short, accurate explanations of "blanszuj," "zeszklij," "zrób zasmażkę") is real editorial work, not engineering, and shouldn't be underestimated as "just a dictionary."

## 4. Recipe Acquisition 2.0: Importing from Video & Social Platforms

**The findings.** Classic recipe-manager parsers (Paprika is the named market leader) rely on Schema.org `Recipe` structured-data tags embedded in a webpage's HTML — a well-solved problem for blogs and recipe websites. That entire mechanism is **useless** against TikTok, Instagram Reels, and YouTube Shorts, where ingredients and technique are conveyed via spoken narration or loose text overlaid on video frames, with no structured metadata at all. Instagram/Pinterest support is partial (often requires an external login just to read a caption). TikTok/Shorts support is described as "no man's land" — completely unsupported. The report's own headline technical ask: apps should use multimodal AI (LLM + Vision) to transcribe audio (e.g. via a Whisper-class model), run OCR on on-screen text overlays, and consolidate the result into a clean, structured ingredients/steps format. Separately: parsers routinely fail against paywalled quality-journalism recipe pages (only a minority of apps ship their own embedded browser to work around this), and scrape "junk ingredients" — random SEO/marketing phrases picked up from a blog's page footer — into the ingredient list, requiring tedious manual cleanup before a recipe is usable.

**Where this sits relative to Foodia — a foundational gap this report surfaces, not just an incremental one.** Worth stating plainly: **Foodia has no recipe-creation or import flow of any kind today.** Every recipe is a hand-authored fixture in `recipes.mock.ts`. This report describes what a *mature* import pipeline should eventually do (video/AI import), but Foodia's roadmap doesn't yet have the far more basic precursor — a way for a user to add a recipe at all — scoped anywhere. **A short flag pointing here was added to `CLAUDE.md` 4.2** so this foundational gap doesn't stay buried in a futures document; the full staged plan lives here.

**A staged approach, roughly ordered by buildability:**

1. **Manual recipe authoring** (the actual missing precursor) — a "Create Recipe" form producing a real `RecipeDetail`-shaped object: name/summary/description/ingredients/steps, no import, no AI. Genuinely mock-first buildable, and the honest place to start — nothing else in this section works without it existing as a fallback anyway (an AI-imported recipe still needs a form to *review and correct* it in).
2. **URL-paste import from classic websites** — Schema.org `Recipe` JSON-LD extraction from a pasted blog URL. The most tractable of the report's own asks (no multimodal AI needed, just an HTML fetch + structured-data parse) — but genuinely backend-blocked, since a mock-only frontend has no server to run a fetch/scrape from without hitting CORS immediately.
3. **Video import (TikTok/Reels/Shorts) via multimodal AI** — the report's own headline ask. Needs a real LLM/vision API, a real backend, and almost certainly a nontrivial per-call API budget (transcription and vision calls aren't free at scale) — the furthest-out tier, correctly 🔮 P3-or-later.

**My own extension:** whichever import mechanism eventually gets built, the *output* is already exactly `RecipeDetail`-shaped — Foodia's type system doesn't need to change for any of this, only the *ingestion* side does. That's a real, concrete forward-compatibility win from having modeled the recipe graph correctly up front, worth stating as confidence, not just noted in passing. Also worth flagging: "junk ingredients" (SEO spam scraped into fields) is fundamentally a **data-quality/moderation** problem, and it would apply to *any* future user-submitted recipe, not just imports — this connects directly to the community-moderation gap `CLAUDE.md` 4.4 already flags as unbuilt ("moderation... still `2do`'s Report/Problem split, not yet reused here"). Worth solving both at once whenever recipe submission of any kind gets built, not as two separate follow-ups.

## 5. Search, Filtering & Micronutrient Precision *(see also `CLAUDE.md` 4.7, where the buildable core of this section now lives)*

**The findings.** The most concrete, named engineering complaint in the whole report: multi-tag filtering (Paprika named specifically) implements the wrong set algebra. A cook filtering by "Vietnamese cuisine" **AND** "salads" expects the *intersection* — only Vietnamese salads — but gets the *union* (**OR**): every Vietnamese dish (including heavy Pho soups) plus every salad in the whole database (including Greek and Italian). This makes categorization functionally useless once a collection passes a few hundred recipes. Related gaps: no exclusion operator (e.g. "-tomatoes" to filter out a known allergen), and no support for combining several *simultaneous* atypical exclusions (dairy-free **and** low-histamine **and** high-protein at once) — standard binary filters ("gluten-free," "vegetarian") are too shallow for real dietary philosophies, which can be directly contradictory to each other (what's "healthy" for a vegan is the opposite of what's "healthy" for a strict keto or carnivore-diet follower). A further, more specialized ask: separating *added* sugars from *naturally-occurring* sugars (fruit) in micronutrient tracking — important for the large and growing population of diabetics monitoring glycemic impact, and something no reviewed app currently does.

**Why this is the single most "pull-forward-able" idea in the whole report.** Foodia has **zero search or filter UI today** — the home feed applies only the hardware hard-filter (`ownsRequiredEquipment`). But `RecipeCard.tags`/`dietFlags` **already exist** as real fields (string arrays) on every fixture, and are already *rendered* on `RecipeCard.svelte` — they're just never *filterable*. This is about as low-complexity as a real feature gets: the data model is already there, only the UI and the (correct, AND-by-default) filtering logic are missing. **A full module spec for this was written directly into `CLAUDE.md` as a new Section 4.7**, including the AND/OR toggle and exclusion-filter design, explicitly citing this report's own named failure mode as the reason AND must be the default, not an afterthought.

**What stays here, not pulled into `CLAUDE.md`:** the micronutrient precision (added vs. natural sugars) ask needs `MacroSummary` itself to gain a real breakdown, which in turn needs a real nutrition database — already an open, unaddressed gap (`CLAUDE.md` Section 3: "a real nutrition database backing `MacroSummary`... needs a real data source before it can be trusted for anything health-related"). This report doesn't just repeat that gap, it gives it a sharper, health-relevant reason (diabetics tracking glycemic impact) — worth citing as a reason to prioritize solving it once a real backend/nutrition-data source is in scope, but it doesn't change the fact that it's still fundamentally blocked on that same precursor.

## 6. The AI Recipe Adapter — a different AI feature than the Meal Planning Wizard

**The findings.** Growing resistance to dogmatic, undeactivatable "Health Score" labels (Samsung Food named specifically) — a single number a system pins to a recipe based on averaged, often outdated nutrition-pyramid assumptions (e.g. treating all fat as negative, which is absurd for a keto-diet follower), with no way to disable or recalibrate it per the user's own actual dietary philosophy or a real endocrinologist's guidance. The desired alternative, framed as the sector's "Holy Grail": an AI **adapter** — a prompt-driven recipe transformation. Instead of manually searching for a low-fat cheesecake variant, a cook wants to prompt their existing saved recipe directly ("make this high-protein and sugar-free") and have an LLM substitute ingredients in correct stoichiometric proportions, guaranteeing the dish still physically works, and auto-recalculate macros. A real, named risk: AI hallucination — reported incidents where a bot-modified recipe is physically unrealizable (a missing ingredient quantity, a skipped critical thermal step). On the positive side, the report notes LLMs are genuinely strong at cultural/linguistic nuance — e.g. finding a culturally-appropriate Chinese equivalent for "budget meals," accounting for local slang and available ingredients, well beyond a simple dictionary translation. A related ask: dynamic goal calibration (Carbon Diet Coach is named as the model to follow) — instead of a static, once-set calorie goal, auto-adjust weekly macro targets based on real intake and weight-report data.

**A deliberately distinct feature from `CLAUDE.md` 6.2's AI Meal Planning Wizard.** That one generates a whole *week's plan*; this one *transforms a single existing recipe* on demand. Both are genuinely LLM-dependent and 🔮 P3, but worth keeping conceptually separate — the same discipline `CLAUDE.md` already applies elsewhere (Session 6 kept manual content translation and the still-unbuilt AI thread-translation feature, `CLAUDE.md` 6.5, explicitly distinct rather than conflated, precisely to avoid two genuinely different concepts sharing one name).

**A concrete Foodia shape, if this is ever built:** an "🤖 Adapt this recipe" action on the recipe detail page — a prompt input, an LLM call returning a *proposed* new `RecipeDetail`-shaped object (substituted ingredients + adjusted macros), shown for **review, never auto-applied** — the hallucination risk the report itself names makes this non-negotiable. Critically, any substitution candidates the model proposes must be run through the **same allergy hard-filter already established as a non-negotiable architectural rule** in `CLAUDE.md` 4.1/Section 7 ("Allergy safety must be a hard filter, not an AI suggestion the model is merely asked to respect... the one place a bug is a genuine health incident, not a UX annoyance") — that rule was written for the Meal Planning Wizard, but applies with equal force here, and should be implemented once, shared by both features, not reinvented per feature.

**On rejecting Health Scores — worth noting Foodia already gets this right, by construction, not by decision.** `RecipeCard`/`RecipeDetail` has no `healthScore` field anywhere in the type system, and `CLAUDE.md` has never proposed one. This is a case where the external research *validates* an existing design choice rather than surfacing a gap — worth stating explicitly so it isn't mistaken for an unaddressed finding.

Dynamic goal calibration connects to `DietProfile.goals` (already a string array on `UserProfile`) but needs real weight/intake history — which today only lives in ephemeral `localStorage`, with no logging mechanism at all. Genuinely blocked on real accounts/backend, same as most of Section 7 below.

## 7. Social & Family Planning: Decision Fatigue, Swipe-to-Decide, Live Sync

**The findings.** Competing apps are architected for an isolated individual, but daily cooking is deeply relational — partner logistics, kids' preferences (including picky eaters), shared responsibility that current software has ignored for years. "What are we eating tonight" is a recurring, exhausting decision (**decision fatigue**) that disproportionately burdens one person and is a real, named cause of plans collapsing into unhealthy delivery food. The most-wanted, and explicitly *desired at scale*, mechanic: a **Tinder-style swipe** for meal decisions (indie apps SCRAN and Chowy are named as early explorers) — dinner proposals are sent to every household member with the app; each person independently swipes yes/no; a central algorithm silently compiles the responses and picks the consensus match, removing the burden of asertiveness from any one person and shifting the "blame" for the decision onto an arbitrary, objective app. A second, structural gap: **live syncing** — meal planning today resembles distributed workflow management (one partner adds items from a train, another is physically in a store at the same moment), and most apps can't share a single family plan across separate accounts without buying multiple premium licenses; async lag causes duplicate purchases and real financial loss, driving users to abandon specialized tools entirely in favor of copying data into free generic notes apps (Apple Notes, Google Keep, AnyList). A third, more subtle finding: rigid **calendar-grid planning** (locking each meal to a specific weekday) conflicts with real "household flexibility" — many people want to plan 5–6 meals for the week as an unscheduled **pool**, choosing which to cook on a given day based on mood or energy. Samsung Food removing its dateless "weekly queue" feature caused a real, documented user backlash.

**Update, Session 8 — the precursor named below now exists, which changes what's actually blocking this section.** ~~Foodia has none~~ — a real login/register/logout system was built (`CLAUDE.md` 4.8), directly in response to this section's own ❓ item. What that unblocks: `currentUserRef()` now resolves to a real, stable identity when logged in, which is the *identity* half of what every idea in this section needs. What it does **not** unblock, and this distinction matters: none of Profile/Pantry/MealPlan are re-keyed per account — they're still singleton-per-browser, localStorage-only. Logging into the same account from a second device today sees a completely separate, unsynced local dataset. **Real multi-device family sync needs a backend**, not just an account system — the account was the *cheaper, mock-first-buildable* half of the precursor; a sync layer is the *expensive, backend-requiring* other half, and still doesn't exist. Both the swipe mechanic and live sync remain genuinely blocked on that second half.

**One piece is partially buildable today, independent of accounts or sync.** The "flexible weekly queue" (pool-based planning, not locked to a specific day) is a UI/data-model question that doesn't actually require multiple users — it's about whether *one* person's own plan has to be day-locked. Foodia's `MealPlanDay`/`MealSlot` structure is *already* date-locked by design (`MealPlanDay.date`, with `MealSlot`s nested under a specific day) — the report's own account of Samsung Food's user backlash over losing a dateless option is worth taking seriously as a design caution for `/plan`'s existing 7×4 grid, even before any sync work happens. Worth considering, as a future `/plan` UX addition: an "unscheduled this week" pool section alongside the strict grid, letting a recipe be assigned to "sometime this week" without pinning a day — genuinely single-user-buildable, distinct from and not blocked by the swipe/family-sync material.

The swipe mechanic and true live family sync remain genuinely backend-blocked — 🔮 P3-or-later, and honestly probably *later* than most of this document's other 🔮 items, since they depend on infrastructure (real-time sync, a real database) this project hasn't designed at all yet, not just on an API integration. Accounts existing now is real, necessary progress toward this section's own goal — it just isn't sufficient on its own, and shouldn't be mistaken for having closed the gap.

## 8. Trust, Data Sovereignty & the "Enshittification" Risk

**The findings.** This section of the source report is less a feature list than a set of architectural and business-model principles, driven by real, documented user trauma. The report names the phenomenon **"Enshittification"** — platforms degrading a previously-loved product's usefulness in favor of aggressively monetizing a captive, loyal userbase. Concrete, named cases: MyFitnessPal moved its core barcode-scanning feature (once free, once the reason people chose the app at all) behind a paywall while simultaneously thickening the interface with slow background processes and intrusive ads, driving an exodus to lighter competitors (Lose It!, Fitatu). Whisk, acquired by Samsung and rebranded to "Samsung Food," is cited as a trust-destroying M&A case — the rebrand removed a loved feature (the dateless weekly queue, see Section 7 above), ignored bug reports for months, and forced users into a closed corporate account ecosystem. Most viscerally: users of a smaller app called RecipeBox reported **permanent, irretrievable loss of years of personal archived recipes** when the company's management unilaterally switched from free to an $80/year upfront subscription overnight — a real story that "sows a seed of skepticism toward the cloud" across the whole community, not an abstract fear. The report's own conclusion: users want fully local, offline-first data storage with a guaranteed, complete, open-format export path (XML/JSON) as insurance, and show a genuine, strong preference for a one-time/perpetual-license payment (even a relatively high one-time price) over subscription rent, specifically because a subscription is what enables this class of betrayal in the first place.

**Where Foodia already, accidentally, gets this right — worth making deliberate, not just noting as luck.** Offline-first was *already* stated as a real requirement in `CLAUDE.md` Section 1, framed originally around "works in a basement with no signal" — this report independently validates that same architectural choice for a completely different, and arguably more important, reason: trust and anti-enshittification insurance, not just connectivity. And because there's no backend yet, `Profile`/`Pantry`/`MealPlan` already live entirely in `localStorage` — today, Foodia is *already* maximally trust-friendly on this exact axis, simply as a byproduct of being pre-backend, not by deliberate design. **Worth turning that accident into a deliberate, stated principle** the moment a real backend/sync layer gets designed: any future cloud sync should be strictly *opt-in and additive* to local storage, never a replacement that could later be revoked or paywalled — the RecipeBox story above is exactly the failure mode to design against from day one, not retrofit after the fact.

**A genuinely cheap, high-trust feature worth calling out specifically:** Foodia has no data-export mechanism at all today except the shopping list's own plain-text copy (`shoppingExport.ts`). A "download my data" button — a client-side `JSON.stringify` over the existing `localStorage`-backed Profile/Pantry/MealPlan stores, no backend required — would directly serve this report's own explicit ask, is genuinely buildable *now*, and costs very little relative to the trust it signals. Worth considering as a real near-term addition, distinct from everything else in this section that's blocked on business-model decisions the founder hasn't made yet.

**❓ Directly relevant to `CLAUDE.md` 8B's own open monetization question.** That section already asks, unresolved: "which lever ships first — e-grocery affiliate, subscription (AI planning/translation), or tips/royalties?" This report is a real, external, community-sourced data point *against* leading with a subscription model (the community's own stated preference is a one-time/perpetual license, or affiliate/tips-based monetization instead) — worth weighing seriously, not overridden by assumption. This document doesn't presume to decide that question; a short cross-reference to this section was added to `CLAUDE.md` 8B itself so the connection isn't lost.

## Cross-cutting takeaway

The source report's own conclusion, worth restating in Foodia's terms: the market's failures aren't really about *more recipes* or *more features* — they're about **math** (unit consolidation, deduplication, cost-per-serving), **architecture** (pantry/shopping-list/macro-tracker/budget-planner treated as disconnected silos instead of one system), **physical accessibility** (voice, ergonomics, hands that are actually dirty), and **household dynamics** (multi-person reality vs. a solo-user assumption baked into most software).

Foodia's own founding architectural bet — *"a recipe is a graph, not a document"* (`CLAUDE.md` Section 0) — already addresses part of this: node-based comments and community substitutions avoid the "static document" trap this report implicitly critiques elsewhere (rigid Health Scores, undeduplicatable ingredient text). What this report adds is the observation that the **same graph-shaped thinking needs to extend past the recipe itself** — to the **Pantry** (a real, stateful, cross-referenced inventory, not a flat append-only list) and to **Planning** (a flexible, potentially multi-person-aware pool, not a rigid single-owner grid) — to fully deliver on that founding thesis, not just apply it to the one object (the recipe) it was originally designed around.

## 9. Addendum — The Social Layer: Profile, Activity, Privacy, Posting, Upload, Security

**Status — a different kind of entry than Sections 1–8 above.** Everything above this line synthesizes the external 47-Reddit-thread report. This section doesn't — it's an internal design-options pass (24 concepts, four independent directions apiece for six surfaces this app doesn't have at all yet), reviewed and picked from directly by the founder. Recorded here rather than written straight into `CLAUDE.md`'s own P1/P2/P3 buckets for the same reason this whole file exists: a decision on *direction* isn't the same claim as a decision to *build it next* — sequencing against P2's existing backlog (native Capacitor plugins, real e-grocery, full-text search) is still an open call, not made here.

**The starting observation.** Foodia's Recipe Graph already has real social bones — node comments (4.4), substitution/step-alternative voting (4.2/4.9), community translation (4.6), comment moderation (4.4/Session 13). Six adjacent surfaces don't exist at all: nowhere to be a public identity, nowhere to see your own history, no control over who sees what, no way to add content beyond the fixture corpus, no working upload path for a file of any kind, and nothing past a login form for account security. One subsection per gap, each ending in the direction actually picked, not just the options that were on the table.

### 9.1 Public Profile — picked: the Modular Profile

Of the four shapes considered (a browsable Cookbook Shelf grid; a trust-first Kitchen Card leading with `DietProfile`/`HardwareProfile`; a merged cross-store Timeline), the pick is a set of opt-in modules — Recipes, Diet Philosophy, Pantry Highlights, Contribution Badges — each off by default, switched on individually from the same surface as Privacy (9.3). This is Progressive Profiling (4.1) — the existing "never gate, default to the honest neutral state" principle — reapplied to a second surface rather than reinvented for this one. **One explicit adjustment made at pick time, not in the original four options:** the Recipes module ships *on* by default rather than opt-in like the rest — an empty diet bio reads as a normal blank slate, an empty cookbook shelf reads as a broken page, so the one module most visitors are actually there for shouldn't need a first click to appear.

### 9.2 Activity Log — picked: the Private Audit Log first, Category Tabs second

Two of the four options needed a real cross-store merge-sort (a unified stream; a GitHub-style contribution heatmap) that doesn't exist yet and would duplicate itself if built twice for both the profile Timeline (9.1, rejected) and this section. The pick sequences around that cost instead of paying it up front: **the Private Audit Log ships first** — not a public feed at all, a personal-only page (login history, sessions, edits to your own comments/recipes, and moderation actions taken *against* your content). This is the missing other half of Auth (4.8) and Moderation (4.4/Session 13) — today a comment removed by a moderator leaves only a tombstone in its place, with no record anywhere for its own author; this is where that record would actually live, and it's buildable now, reading straight off `commentModerationStore`. **Category Tabs ships next** (Comments / Contributions / Translations / Reactions, each reading its own store with no merge) — matches how the data already lives, and ships incrementally, one tab at a time, rather than waiting on a cross-store aggregation neither the unified-stream nor heatmap options could avoid.

✅ **The Private Audit Log half is built, Session 16** — `/activity` (new route), `lib/utils/activityLog.ts`'s `reportsFiledBy`/`ownCommentsRemoved` reading straight off `commentModerationStore`. Scoped honestly to what's actually real today: reports you've filed (with live status — pending/removed/dismissed), your own comments a moderator has removed, and your current account identity — login/device history and comment-edit history are explicitly named as not-yet-buildable (the first needs a real backend, the second needs a comment-editing feature this app doesn't have) rather than silently omitted. Category Tabs (the rest of this section) remains unbuilt.

### 9.3 Privacy Settings — picked: Presets, with Data Sovereignty pinned above them

The pick is three named bundles — "Just for me," "Home cook," "Public creator" — each expandable into a full per-module matrix for anyone who wants to fine-tune afterward. "Home cook" isn't placeholder copy; it's this app's own stated core persona (Section 0's "time-poor, budget-conscious cook") reused as the preset name instead of invented fresh. Rejected: a single global three-way switch (too coarse once the Modular Profile, 9.1, has more than one thing to hide) and a full per-field matrix as the *primary* surface (real decision-fatigue risk — this file's own Section 7 already names exactly this failure mode in a competing product, and the caution applies here just as much). **A structural decision made at pick time:** the "download everything" / "delete my account" block from the fourth option (Data Sovereignty First) isn't a fourth alternative competing with the presets — it's pinned above all three of them, always visible regardless of which preset is active. Trust controls shouldn't be one of three choices a user might not click into; this is the already-flagged "download my data" feature (Section 7 item 22, and this file's own §8 RecipeBox story) with a visibility layer built around it, not a separate idea, and the one genuinely backend-free piece of this whole section — a client-side `JSON.stringify` over the existing `localStorage`-backed Profile/Pantry/MealPlan stores.

✅ **The download half is built, Session 16** — `lib/utils/dataExport.ts`, surfaced on `/onboarding` (this app's de facto profile page) whenever any real data exists. The "delete my account" half and the three presets themselves (the actual visibility-control layer this section is named for) remain unbuilt — what shipped is specifically the one piece already flagged as cheapest and most backend-free, not the whole section.

### 9.4 Posting & New Content — picked: Recipe-First Composer, then Cooked It

`CLAUDE.md` 4.2 already states in writing that "there is currently no way for a user to create or import a recipe at all" — this section's first pick just closes that named gap: a staged wizard (Basics → Ingredients → Steps → Publish) producing a real `RecipeDetail`, no import, no AI, matching the precursor this file's own Section 4 (item 1) already specced. **Nothing else in this section works without it existing first**, including this section's own second pick. That second pick, "Cooked It" — a low-friction photo+rating+one-line post tied to a recipe already in the user's `MealPlan` — is deliberately sequenced right behind it, since it's nearly free once `MealSlot` gains any "cooked" state at all, which Section 1 (item 4) already specs for pantry auto-deduction independent of this. Building that state once serves both features, not two separate efforts. **Deliberately deferred, not cut:** a multi-format composer (Recipe/Photo/Tip/Question as sibling content types) and a node-by-node draft composer that would extend "a recipe is a graph, not a document" to the authoring side itself — both real, both correctly v2, neither blocking anything above them.

✅ **The Recipe-First Composer is built, Session 18** — with one real upgrade past the original pick: not a staged wizard but a single-page editor with genuine drag-and-drop reordering for both ingredients and steps (native HTML5 DnD). Proven end-to-end by importing 3 real recipes from a real external source (aniagotuje.pl) under a real registered account, not synthetic test data — see `CLAUDE.md`'s own Session 18 build-log entry. "Cooked It" (this section's own second pick) remains unbuilt, still blocked on `MealSlot` gaining a cooked state (Section 1 item 4).

### 9.5 Working Upload — picked: Local-First Capture Queue, landing on Direct-to-Storage

**The one section of this whole addendum that stays genuinely backend-blocked** — none of its four options are mock-first buildable the way nearly everything else this app has shipped has been, since there's no Django endpoint yet to request a signed URL from or proxy a file through. The pick is really two halves of one pipeline, not a single choice among four: on the client, photos/video save to the device the instant they're captured (Capacitor Filesystem), usable offline immediately, queued for background upload the moment connectivity returns — the literal upload-side implication of Section 1's own "offline-first is a real requirement... works in a basement with no signal" line, just never applied to the upload direction before now. On the (future) server side, the file lands via a short-lived signed URL straight to object storage — R2 is the natural pick given this app already deploys to Cloudflare (`wrangler.jsonc`). **Two real upgrades intentionally not picked as starting points, just deferred:** a server-proxied pipeline that runs EXIF-stripping and moderation before anything is stored (the natural photo-side extension of the comment moderation system already built in 4.4/Session 13, worth doing the moment a backend exists — a phone photo's EXIF can carry GPS coordinates, worth stripping unconditionally, not opt-in), and resumable chunked upload for anything video-length, worth building specifically once video content (this file's own Section 4 video-import ambition, or just longer cooking clips) is actually in scope, not before.

### 9.6 Account Security — picked: the Baseline now, inside a Trust & Safety Center frame, with Passkeys as the real target

`AUTH_ACCOUNTS` (`CLAUDE.md` 4.8) already states plainly that it's "genuinely not a credential store" — plaintext mock passwords, a cookie holding a bare user id, no hashing, no real session token, explicitly flagged as needing "a complete rebuild the moment a real backend exists" (Section 7 item 25). The pick works within that honesty rather than around it: **build the Baseline now** (change password, active sessions/devices with per-device sign-out, login history) — the only one of the four options meaningfully buildable against today's mock auth, and the direct UI half of that already-flagged rebuild. **Build it inside the fourth option's frame from day one** — a Trust & Safety Center that also holds blocked/muted users, data export/delete (9.3's pinned block), and a genuinely new piece: your own report history. `/moderation` (4.4/Session 13) already exists for the moderator reviewing a filed report; nothing exists for the person who *filed* it, who today gets no visible outcome at all once they tap "🚩 Zgłoś." Choosing the container now avoids redesigning it later once more belongs inside it. **Two-factor TOTP is explicitly skipped, not merely deferred** — the pick goes straight to passkeys/WebAuthn as the real target once a real backend and native Capacitor platforms (6.1, still unscaffolded) both exist, since it sidesteps the exact honesty gap `AUTH_ACCOUNTS` already carries (no plaintext password to have been dishonest about, if there's no password at all) rather than bolting standard 2FA onto a credential store already on record as needing a full rebuild anyway.

**Sequencing, stated plainly.** Four of these six picks have a genuinely mock-first-buildable first move today, no backend required: the Modular Profile (9.1), the Private Audit Log (9.2), Presets + data export (9.3), and the Recipe-First Composer (9.4). One (Account Security, 9.6) has a buildable-now cosmetic layer sitting on top of a component already flagged for a full rebuild. One (Upload, 9.5) has no buildable-now path at all. That ordering — not the four-options-per-surface framing itself — is the part worth carrying into whatever P2 planning pass actually sequences this against the rest of the existing backlog (native Capacitor plugins, real e-grocery, full-text search).
